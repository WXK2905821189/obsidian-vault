# AGENTS.md 编写规范

你在 Claude Code 里精心写了一篇 CLAUDE.md，把技术栈、构建命令、代码约定写得清清楚楚。周一队友在 Cursor 里打开同一个仓库，AI 完全不认识这些指令；周三你换到 Windsurf，一切回到原点。指令文件成了工具的私有品，换一次工具就要重写一遍。

这不是你写得不好，是标准的问题。CLAUDE.md 是 Claude Code 的私有格式，Cursor 认 .cursor/rules，Copilot 认 copilot-instructions.md。一套知识被困在一个工具里，恰恰是 [[01-AI技术/Skill制作痛点/07_跨平台兼容性挑战|跨平台兼容性]] 问题在指令文件上的重演：写一份能用，换环境就废。

## AGENTS.md 是什么

AGENTS.md 是 2025 年发布的跨厂商开放标准：纯 Markdown、无 frontmatter、放在仓库任意层级。目前已有约 6 万个开源项目采纳，覆盖 18 到 24 个 Agent 工具。它解决一个核心问题：把"这个仓库怎么工作的普适事实"从工具里剥离出来，写成任何 Agent 都能读的文本。

定位上要分清三层：

- AGENTS.md 承载普适事实：技术栈、构建与测试命令、目录约定、代码风格。
- 工具专属内容（某个 IDE 的交互偏好、某个 Agent 的模型参数）放工具自己的配置文件。
- 项目动态状态（当前进度、待办、最近决策）不属于指令文件，属于 [[05-产品与开发/AI驱动Web应用开发/02-文档体系篇/02_项目记忆文档|项目记忆文档]]。

> [!tip] AGENTS.md 的写作心法只有一句：只写"任何一个 AI 打开仓库都该知道的、且相当长一段时间不变的事实"。会话相关的动态信息一律别放进来。

## 层级加载规则

AGENTS.md 的加载不是"读一个文件"，而是"从全局到仓库根再到子目录逐层拼接"：

1. 全局层：`~/.agents/AGENTS.md`，你所有项目共享的通用约定。
2. 仓库根：`<repo>/AGENTS.md`，整个仓库的事实。
3. 子目录层：`<repo>/src/AGENTS.md`、`<repo>/src/components/AGENTS.md`，逐级向下。

Agent 从全局层开始，一层一层读下来并拼接成一份组合上下文。这意味着你可以在 `src/` 里放一篇只讲前端约定的 AGENTS.md，不必把前端内容塞进根文件。这套"越具体越靠下"的组织方式和 [[01-AI技术/AI Agent 工具/AI_Agent_赛道一_终端CLI编程Agent|终端CLI编程Agent]] 的目录扫描习惯天然配合，Agent 走进哪个目录就读哪层的规则。

另有 `AGENTS.override.md`：放在某层时用整层替换而不是拼接，适合子目录风格与仓库根冲突的极端情况，平时基本用不上。

每个文件有默认 32 KiB 的上限，超出会被截断。这既是约束也是提醒：一个层级放不下，就拆到下一级子目录，而不是硬塞。

> [!tip] 拼接机制决定了信息放置的黄金法则：越通用的放越上层，越局部的放越下层。全局层放"提交信息规范"，仓库根放"构建命令"，`src/api/` 里放"API 错误处理约定"。

## 内容取舍原则

写什么、不写什么，比怎么写更重要。三条取舍原则：

**只放每个会话都需要知道的普适事实。** 构建命令、测试命令、代码风格、目录结构，每个会话开头 AI 都要靠这些进入状态。某个功能的一次性上下文不属于这里。

**指令要具体可验证。** "代码质量要好"是废话，"Python 代码用 4 空格缩进、类型注解必填、函数要带 docstring"是可执行的。AI 对含糊指令的"遵从"其实是随机发挥。

**细节走渐进式披露。** 常驻的 AGENTS.md 保持在 200 到 300 行以内；专项知识（部署流程、迁移计划）放独立文档，在 AGENTS.md 里用一行说明"部署细节见 docs/deployment.md"。这与 [[01-AI技术/超长项目AI跑/02_上下文管理：AI的记忆体系|AI的记忆体系]] 的分级思想一致：常驻层只留高频信息，低频信息按需读。

除了三条原则，还有一张负面清单，以下内容一律别进 AGENTS.md：

- 会话进度与待办：这是动态状态，属于 [[05-产品与开发/AI驱动Web应用开发/02-文档体系篇/02_项目记忆文档|项目记忆文档]]。
- 个人偏好与本地路径：写进工具专属文件或用户级配置。
- 一次性修复指导："这个问题的改法如下"属于聊天记录，不属于规则。
- 与具体工具绑定的命令：例如某个 IDE 的专属快捷键，换工具即失效。

## 官方示例拆解

Anthropic 官方仓库的 AGENTS.md 结构值得照抄：

```
# AGENTS.md

## 项目简介
三句话讲清仓库做什么、怎么跑起来。

## 构建与测试
- 构建：`npm run build`
- 测试：`npm test`
- Lint：`npm run lint`

## 目录结构
src/        源码
tests/      测试
docs/       文档

## 代码约定
- TypeScript 严格模式
- 组件用函数式写法
- 提交信息遵循 Conventional Commits
```

注意它没有 frontmatter，没有工具专属参数，没有"你必须""你要听话"这类训导句。全部是可验证的客观陈述。官方建议直接以这个骨架起步，先跑通再增补。

## 与 CLAUDE.md 的关系

AGENTS.md 和 CLAUDE.md 是"标准与实现"的关系。Claude Code 现在也认 AGENTS.md，两者都放在仓库根时，Claude Code 会把两个文件都读入上下文。

最省事的兼容做法是一个文件两处引用：

```bash
ln -s AGENTS.md CLAUDE.md   # 同一内容，两个入口
```

以 AGENTS.md 为唯一事实源，CLAUDE.md 作为指向它的符号链接。这样 Claude Code 拿到的是同一套规则，换到任何支持 AGENTS.md 的工具也不损失信息。想给 Claude Code 单独加偏好，再建一个轻量的 `CLAUDE.local.md`，别在链接文件里动刀。

## 完整模板

以下模板覆盖一个中小型仓库的典型需求：

```markdown
# AGENTS.md

## 项目简介
<三句话：做什么、为谁做、怎么跑起来>

## 构建与测试
- 安装依赖：`pnpm install`
- 本地开发：`pnpm dev`
- 构建：`pnpm build`
- 测试：`pnpm test`（含类型检查）
- Lint：`pnpm lint`

## 目录结构
<主干目录一行一个，注明职责>

## 代码约定
- <语言>、<缩进>、<命名规则>
- <测试命名与组织规则>
- <提交信息规范>

## 工作流
- 修改后必须跑测试再提交
- 新增依赖前先问维护者

## 注意
- <常见坑、禁止事项、安全提示>
```

模板写完后逐条自检：这一条是不是"每个会话都该知道"？换工具后还成立吗？三个月后还成立吗？三个"是"才留下。

文件会过时，约定三个更新时机：技术栈变更当天更新构建命令；约定被打破时先改文件再改代码；每次大重构后通读一遍删掉过时内容。没有更新时机的指令文件，半年后就是一份错误手册。

## 现在你应该怎么做

1. 在 `~/.agents/AGENTS.md` 写下你所有项目共享的通用约定（提交信息、分支命名、代码风格底线），十条以内。
2. 在仓库根新建 AGENTS.md，照官方骨架填"项目简介、构建与测试、目录结构、代码约定"四节。
3. 有局部内容的子目录（如 `src/api/`）放一篇短的子目录 AGENTS.md，根文件不提及。
4. 执行 `ln -s AGENTS.md CLAUDE.md`，让 Claude Code 共享同一份规则。
5. 开一个全新会话验证：看 AI 是否自动说出正确的构建命令与代码约定；不满足就回来改文件，直到它"一看就懂"。
