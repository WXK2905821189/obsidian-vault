# 跨工具统一策略

你把项目从 Claude Code 迁到 Cursor，发现 CLAUDE.md 里的指令大多失效；半年后公司统一换 Windsurf，又得重来一遍。每次换工具都要重写指令文件，就像把 [[01-AI技术/Skill制作痛点/07_跨平台兼容性挑战|跨平台兼容性]] 的教训重新踩一遍——写一份能用，换环境就废。

核心问题在于把"仓库事实"和"工具行为"写进了同一个文件。前者换工具不变，后者随工具变。分开管理，迁移成本就能从"重写"降为"写个适配层"。

## 统一策略：核心加适配层

策略一句话：**AGENTS.md 为核心，工具专属文件做适配层**。

- 核心：AGENTS.md 只写跨工具通用的仓库事实——技术栈、构建命令、目录约定、代码风格、禁止事项。
- 适配层：各工具自己的文件（CLAUDE.md、.cursor/rules、copilot-instructions.md）只写该工具特有行为，并指向核心。

适配层的文件内容写"规则见 AGENTS.md，仅补充本工具以下特有约定"，把 AGENTS.md 变成唯一事实源。各工具文件的触发方式各不相同，[[01-AI技术/AI Agent 工具/AI_Agent_赛道一_终端CLI编程Agent|终端CLI编程Agent]] 对比过各家的机制，适配层正是用来消化这些差异的。

> [!tip] 核心与适配层的边界判定：这条规则换工具后还成立吗？成立，进 AGENTS.md；只在某个工具里成立（比如某 IDE 的快捷键约定），进适配层。

## 一套文档在多工具间复用

以 AGENTS.md 为核心，各工具按自己的机制接入：

- **Claude Code**：`ln -s AGENTS.md CLAUDE.md`，或写一行 CLAUDE.md 指向根文件；工具特有偏好放 `CLAUDE.local.md`。
- **Cursor**：规则文件里 `alwaysApply` 一条"本仓库规则以 AGENTS.md 为准"，普适内容不再复制。
- **Copilot**：`.github/copilot-instructions.md` 开头写明"仓库约定见 AGENTS.md"，只保留请求级轻量约束。
- **Windsurf**：支持全局规则与 AGENTS.md，同样以引用为主。

四个工具的接入方式不同，但内容来源只有一个。改动时只动 AGENTS.md，各适配层文件基本不动。

## 一个仓库的完整布局

统一策略落到磁盘上，是一个核心加四个适配层：

```
repo/
├── AGENTS.md                      # 核心：唯一事实源
├── CLAUDE.md -> AGENTS.md         # Claude Code 适配层（符号链接）
├── CLAUDE.local.md                # 本地私有，不提交版本库
├── .cursor/rules/global.mdc       # Cursor 适配层：指向 AGENTS.md
└── .github/copilot-instructions.md  # Copilot 适配层：两页内
```

核心一份，适配层各一小份，加起来就是一个仓库的完整指令体系。任何新工具、新同事进来，读 AGENTS.md 就能进入状态；任何一次规则更新，改一个文件就同步到全部工具。这套结构与 [[01-AI技术/AI Agent 工具/AI_Agent_赛道一_终端CLI编程Agent|终端CLI编程Agent]] 生态里"标准协议加各家实现"的格局同构，标准负责稳定，实现负责差异。

## 工具专属文件最少化

适配层的铁律是"最少化"：每个工具专属文件只保留别的工具用不到的少数几条，能引用就引用，能空就空。

最少化的度量标准：适配层文件加起来不超过 AGENTS.md 的十分之一。如果 CLAUDE.md 里躺着 50 行 Cursor 没有的内容，先问这些内容是不是真的工具专属——大概率是"仓库事实"放错了地方。

> [!tip] 每次换工具时的痛苦程度，正比于适配层文件的体积。适配层越薄，迁移越顺；这也是统一策略与"每工具一份大而全规则"的根本区别。

## 反模式清单

统一策略最常见的三种反模式：

- 复制粘贴式：AGENTS.md 的内容在 Cursor 规则里又抄了一份，改一处漏一处，两处开始互相矛盾。
- 只有适配层没有核心：各工具文件各写各的，没有一份"通用事实"，换工具等于推倒重来。
- 核心膨胀：AGENTS.md 越写越长，超过 300 行后逐步退化成文档，适配层反而比核心干净。

三条反模式的共性是违背"单一事实源"。检查方法：任何一条规则出现在两个以上文件里，就是反模式的信号，当天归位。

## 迁移清单：换工具五步

换工具时按清单走，半小时内完成迁移：

1. 盘点：列出现有各工具指令文件，逐条标注"通用事实"或"工具专属"。
2. 归位：通用事实合并进 AGENTS.md，工具专属内容留在原文件待删。
3. 瘦身：写新工具的适配层文件，内容只含该工具特有约定加一行指向 AGENTS.md。
4. 验证：开新会话，用三个问题检验——AI 能说出正确构建命令吗？代码风格对得上吗？常见坑避开了吗？
5. 清理：删除旧工具专属文件中已归位的内容，保留一份归档副本以备回迁。

这五步与 [[01-AI技术/LOOP Engineering/03-架构篇/03_Hook Loop Harness范式|Hook Loop Harness]] 的思路同源：核心逻辑与外围适配分离，迭代时只动该动的地方。

> [!tip] 迁移演练的价值不在"换工具"本身，而在暴露核心与适配层边界划错的地方。演练时每删一条适配层规则，都是对边界的一次重新校准。

## 文档与指令文件的分工边界

统一策略之上还有一层更大的边界：文档与指令文件。

- 指令文件（AGENTS.md 及各适配层）回答"AI 该怎么做"：规则、约束、工作流。
- 项目文档（[[05-产品与开发/AI驱动Web应用开发/02-文档体系篇/02_项目记忆文档|项目记忆文档]]、架构文档、设计文档）回答"项目是什么"：事实、状态、决策。

[[01-AI技术/超长项目AI跑/02_上下文管理：AI的记忆体系|AI的记忆体系]] 把项目知识分成多级，指令文件处于最高频读取的那一级。判别口诀照旧：能用"是"回答的进文档，能用"应该、必须"回答的进指令文件。两者构成完整闭环：文档供给事实，指令文件约束行为，AI 在约束下使用事实。

把口诀展开成一张归类表，写文件时对照着放：

| 内容示例 | 归属 | 判定 |
| --- | --- | --- |
| 技术栈、目录结构、当前状态 | 项目文档与记忆文档 | 用"是"回答 |
| 代码风格、构建命令、禁止事项 | 指令文件 | 用"应该、必须"回答 |
| 某工具的专属偏好 | 工具适配层 | 换工具后不成立 |
| 会话内的临时决定 | 会话总结或 Auto Memory | 只对本会话有意义 |

## 现在你应该怎么做

1. 建立 AGENTS.md 核心文件：技术栈、构建命令、代码约定、禁止事项，逐条验证"换工具仍成立"。
2. 把各工具专属文件瘦身为适配层，每份只留工具特有内容加一行"规则以 AGENTS.md 为准"。
3. 用符号链接或一行索引让 Claude Code、Cursor、Copilot 接入同一事实源。
4. 与团队约定：新约定先写入 AGENTS.md，再决定哪些工具需要适配层补充。
5. 每季度做一次迁移演练：假设换工具，按五步清单走一遍，让迁移能力变成习惯而不是灾难。
