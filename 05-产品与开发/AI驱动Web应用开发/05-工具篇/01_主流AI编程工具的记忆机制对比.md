# 主流AI编程工具的记忆机制对比

你问过所有用过 AI 编程工具的人同一个问题：Claude Code、Cursor、Cline、GitHub Copilot，谁的记忆最强？答案五花八门，有人力挺 Cursor 的规则系统，有人说 Cline 的 Memory Bank 才是正道，还有人坚信 Claude Code 的自动记忆无人能敌。但当你真的换了三个工具就会发现一件反直觉的事：所有工具默认都没有跨会话记忆。关掉对话，一切归零。所谓"记忆最强"，从来不是工具自带的属性，而是你维护文件的函数的输出结果。

> [!tip] 关键洞察
> 把"谁的记忆最强"翻译成"谁最方便我把记忆写进文件"，问题才算问对了。四款工具默认都不记住任何东西，差异只在于：文件放在哪、什么时候加载、能装多少内容、会话断了怎么接。

## 四维度对比表

记忆机制可以拆成四个可比的维度：指令文件机制（项目规则放哪、怎么加载）、自动记忆（工具是否主动读写记忆文件）、会话续接（对话断了怎么恢复）、上下文压缩（上下文撑爆时怎么办）。

| 维度 | Claude Code | Cursor | Cline | GitHub Copilot |
|------|-------------|--------|-------|----------------|
| 指令文件机制 | CLAUDE.md 四级体系：全局、项目、子目录逐级叠加 | .cursor/rules/*.mdc，alwaysApply/globs/description 三种触发方式 | .clinerules + Memory Bank 六文件 | copilot-instructions.md 仓库级常驻 + 路径级 instructions + prompt files |
| 自动记忆 | Auto Memory：写入 ~/.claude/projects/项目/memory/，MEMORY.md 做索引，每会话载入前 200 行或 25KB | 无。模型不保留记忆，持久上下文完全靠规则注入 | Memory Bank 六文件，配合 /newtask 主动读写 | 无独立自动记忆文件系统 |
| 会话续接 | claude --continue/-c 续当前会话，claude --resume/-r 恢复指定会话 | IDE 内对话历史，无专门命令行续接 | /newtask 把计划、决策、下一步打包进新任务，官方称"消除上下文窗口限制" | 靠 IDE 内对话历史 |
| 上下文压缩 | /compact 压缩当前会话上下文 | 自动截断，用户无干预 | Auto Compact + Focus Chain 分阶段聚焦 | 自动截断 |

表格看完要分清两类能力。指令文件机制和自动记忆解决"记住什么"，会话续接和上下文压缩解决"忘了之后怎么办"。前两类决定工具的静态记忆容量，后两类决定长会话的续航能力，两者缺一不可。

## Claude Code：四级体系与自动记忆

Claude Code 的 CLAUDE.md 按四级加载：全局 ~/.claude/CLAUDE.md 管个人偏好，项目级 ./CLAUDE.md 管仓库约定，子目录级管局部模块，import 机制允许复用公共片段。层级越深优先级越高，同名指令就近覆盖。这套体系在 [[05-产品与开发/AI驱动Web应用开发/03-上下文篇/02_CLAUDE.md编写规范|CLAUDE.md]] 里展开过，写法要诀是短、具体、可执行。

Auto Memory 是它区别于其他三款的标志性功能。工具会把值得长期记住的内容写进 ~/.claude/projects/项目/memory/ 目录，MEMORY.md 作为索引文件，每个会话启动时载入前 200 行或 25KB。配合 /compact 压缩长会话、--continue 和 --resume 接续断开的对话，Claude Code 在"长任务续航"这个维度上是四款工具里最完整的。代价是记忆文件分散在用户主目录，不进仓库，团队共享时这套记忆是各人私有的。

## Cursor：规则注入型

Cursor 不写任何记忆文件，它把一切押在 .cursor/rules/ 目录的 .mdc 文件上。每个规则文件声明三种触发方式：alwaysApply 每次会话无条件注入，globs 按文件路径匹配注入，description 由模型按语义决定是否使用。这种设计的哲学是：模型不需要记住项目，只需要在每次对话开始时有足够的规则说明项目。

长处是规则与代码同库、同版本控制，团队协作时规则天然共享，规则本身即文档。局限也明显：每次会话都要重新注入全部规则，规则一多，注入开销变大，且规则写得再细，模型对"项目为什么长这样"的理解依然停留在规则字面，无法沉淀动态的项目状态——今天做到哪一步、哪个决定推翻了旧方案，Cursor 一概不知。

## Cline：Memory Bank 与 newtask

Cline 的 Memory Bank 把项目记忆拆成六个文件：projectbrief（项目目标）、productContext（产品背景）、systemPatterns（系统模式）、techContext（技术上下文）、activeContext（当前工作状态）、progress（进度）。六份文件各管一个维度，activeContext 和 progress 随会话推进持续更新，另四份保持相对稳定。

真正有特色的是 /newtask：把当前会话的计划、决策、下一步动作打包进新任务，官方宣称以此"消除上下文窗口限制"。配合 Auto Compact 和 Focus Chain 的分阶段聚焦，Cline 适合把同一件事分多天、多会话推进。局限是 Memory Bank 维护成本高，六个文件不是摆设，不勤更新就退化成六份过期的摆设。它把"记忆是维护出来的"这句话贯彻到了极致。

## GitHub Copilot：指令注入优先

Copilot 走的是最保守的路线：仓库级 copilot-instructions.md 常驻注入，路径级 instructions 按目录补充，prompt files 为特定任务提供提示词模板。没有独立记忆文件，不主动写入任何项目状态。它的角色定位是 IDE 内的补全助手，不是长任务的执行者，所以记忆需求天然更低。

## 文档体系与工具机制如何配合

四款工具的机制各不相同，但配合方式有一条统一规律：**工具负责加载，文档负责内容**。工具决定文件在哪里、什么时候被读进上下文，你决定文件里写什么。机制再强，文件里没有内容等于没有记忆；内容再好，工具不加载等于没有文件。

落地时把记忆分层：全局层写个人偏好，项目层写仓库约定，会话层写进度与状态。Claude Code 的四级体系和 Cline 的六文件结构天然对应这三层，Cursor 和 Copilot 则用规则文件承担前两层，会话层靠你手动写 Session Summary 或进度文档补上——这正是 [[05-产品与开发/AI驱动Web应用开发/02-文档体系篇/07_会话交接与变更日志|会话交接与变更日志]] 存在的意义。更底层的记忆原理，参见 [[01-AI技术/AI Agent开发实战/03_记忆与上下文管理：让Agent记住你是谁|Agent记忆机制]]。

> [!tip] 关键洞察
> 别让工具的机制差异决定你的记忆策略。最稳的组合是：项目里始终维护一份 AGENTS.md 或 CLAUDE.md 做常驻约定，配 docs/ 目录存状态类文档，再借用各工具的自动机制做增量补充。文档体系是主干，工具机制是枝叶。

## 现在你应该怎么做

1. 打开你常用的工具，找到它的指令文件加载规则：Claude Code 看 CLAUDE.md 的层级，Cursor 看 .cursor/rules 的三种触发方式，Cline 看 .clinerules 和 Memory Bank，Copilot 看 copilot-instructions.md，搞清楚文件放哪、何时加载。
2. 对照四维度表格，给当前工具打一次分：指令文件是否在版本控制里、自动记忆是否需要手动维护、会话断了能否续接、上下文撑爆是否有对策。哪项是短板，哪项就是你最该用文档补的位置。
3. 只维护一份常驻指令文件，把它写短写具体，作为所有工具的公共底座。
4. 下一个长会话结束前，试验一次该工具的续接能力：Claude Code 用 --continue，Cline 用 /newtask，把"续接是否顺畅"作为继续使用该工具的判断依据。
