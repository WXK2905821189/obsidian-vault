# 主流AI编程工具的选型矩阵

你刚接了一个周末要上线的小工具，同时挂着公司一个要改 40 个文件的旧仓库。朋友圈里有人用 Claude Code 写完整个后端，同事用 Cursor 三小时改完一套 UI，播客主播说他靠 Cline 的 Memory Bank 管了三个月长项目。你打开三款工具的官网，越看越不知道怎么选。选型困境的根源，是把"哪个工具最强"当成单选题，而真实的答案是：每个工具都有一个主场，选型的第一步是先分清你的任务属于哪个主场。

> [!tip] 关键洞察
> 工具不是互相替代的关系，是分工的关系。终端 Agent 负责长任务执行，IDE 工具负责补全与局部修改。把工具配到它擅长的任务类型上，比纠结"谁更强"收益大得多。

## 先给任务分类

选型之前，先给日常任务贴标签。任务分类只问两个问题：任务要跑多久、任务的上下文有多大。

- 长任务：从头写一个模块、跨文件重构、打通一条完整流程，动辄数百行改动，需要多轮迭代
- 短任务：改一个函数、调一个样式、修一个报错，三五分钟见分晓
- 补全型：边写边补，你出思路，工具填实现
- 探索型：不知道方案对不对，需要工具先读代码、给方案，再动手

长任务对会话续航和记忆能力敏感，补全型对响应速度和 IDE 集成敏感，探索型对读码能力和解释能力敏感。四类任务的偏好各不相同，这就是选型矩阵的横轴。

## 按场景选型

| 场景 | 首选 | 备选 | 理由 |
|------|------|------|------|
| 终端长任务 | Claude Code | Cline | 四级指令体系 + Auto Memory + --continue/--resume，会话续航最完整；Cline 靠 Memory Bank 和 /newtask 亦可胜任 |
| IDE 内补全 | Copilot | Cursor | 常驻注入、延迟低，不打断打字流；Cursor 补全能力同样在线 |
| 多文件重构 | Claude Code | Cursor | 重构需要全局视野和跨文件改动，终端 Agent 的一次性改动能力最强；Cursor 的 agent 模式可做备选 |
| 移动端 / 远程 | Cline | Claude Code | Cline 作为 VS Code 扩展可随 IDE 远程开发走；Claude Code 的 SSH 模式是另一种解法 |
| 短任务 / 快速修改 | Cursor | Copilot | IDE 内就地修改、即时看到 diff，成本最低 |
| 探索型读码 | Cursor | Claude Code | IDE 的代码导航与引用跳转更顺手，Claude Code 读码能力不弱但体验不如编辑器 |

表格有一个隐藏规律：任务的"长度"决定工具的上限。一个能续接会话、压缩上下文、维护记忆文件的工具，上限高；一个只做补全的工具，上限低但轻快。长任务交给上限高的，短任务交给轻快的，错配才是最大的浪费。

## 个人开发者的推荐组合

个人开发者不需要只留一个工具，推荐组合是"终端 Agent + IDE 工具"各配一个，职责分开：

- 主战：终端 Agent（Claude Code 或 Cline），负责写模块、重构、跑测试、处理长任务。它在仓库根目录读取 AGENTS.md / CLAUDE.md，产出完成后更新进度文档。
- 副战：IDE 内补全（Copilot 或 Cursor），负责边写边补、小修改、看代码。它不该被要求做跨文件大重构。
- 分界线：改动超过 30 行或涉及 3 个以上文件，从 IDE 切到终端 Agent；少于 30 行，留在 IDE。

两个工具共用同一份仓库文档，就不会出现"终端里的 AI 遵循一套约定、编辑器里的 AI 遵循另一套"的割裂。具体写法参考 [[05-产品与开发/AI驱动Web应用开发/03-上下文篇/01_AGENTS.md编写规范|AGENTS.md]]，这份文件就是两把工具的共用底座。工具各自的机制差异，对照 [[01_主流AI编程工具的记忆机制对比|记忆机制对比]] 理解即可，不影响组合本身。

## 选型后的文档适配步骤

工具定下来，紧接着按工具重排仓库文档，让指令文件与工具的加载方式对齐：

1. 读工具的加载规则：Claude Code 看 CLAUDE.md 层级，Cursor 看 .cursor/rules 的触发方式，Cline 看 .clinerules，Copilot 看 copilot-instructions.md。
2. 写一份常驻指令文件放仓库根目录，内容限定为构建命令、测试命令、目录约定、关键约束，控制在 30 行以内。
3. 需要工具自己写状态时，指定一个状态文件路径（如 docs/progress.md 或 Cline 的 Memory Bank 目录），让工具把"做到哪、下一步"写进去。
4. 用三个真实任务试运行，检验工具是否真的读到了文档：故意在文档里写一条错误约定，看工具会不会遵守，不遵守就说明加载没生效。

> [!tip] 关键洞察
> 换工具的真正成本不在安装和学习，而在文档适配。工具加载规则变一次，仓库文档就要跟着调一次。文档写得越贴近"纯约定、不绑定工具"，换工具的迁移成本就越低。

## 换工具的成本评估

换工具不是零成本动作，评估四笔账再决定：

- 文档账：原工具的专属文件（.cursor/rules、.clinerules）能否映射到新工具。纯约定类内容（构建命令、代码规范）映射成本低，工具强绑定内容（Memory Bank 六文件结构）映射成本高。
- 记忆账：已有会话里没落盘的决策与进度会随换工具丢失。换之前先把进度文档、决策记录补齐，[[05-产品与开发/AI驱动Web应用开发/02-文档体系篇/05_决策记录ADR|ADR]] 类内容不绑定工具，永远可迁移。
- 习惯账：工作流重学一遍的成本，通常被低估。别因为一次体验不佳就换，先确认问题在工具还是在自己的文档体系。
- 迁移顺序：先并行试用一周，新工具和旧工具同时用，同一类任务两边各跑一次对比结果，确认胜出再彻底切换。

## 现在你应该怎么做

1. 把最近两周的任务列出来，按长任务、短任务、补全型、探索型分类，统计每类占比。
2. 对照选型矩阵，找出你占比最高的两类任务，确认当前工具是否在对应场景的推荐列里。
3. 如果你只有一个工具，按"终端 Agent + IDE 工具"的组合补上缺的那个，先小任务试用一周。
4. 为你的主战工具写一份仓库根目录指令文件，并指定状态文件路径，跑三个真实任务验证加载生效。
5. 把这条选型结论连同理由写进项目文档，三个月后工具市场变了，回来看这篇文章重新评估一次。
