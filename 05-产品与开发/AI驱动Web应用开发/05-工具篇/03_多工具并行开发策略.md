# 多工具并行开发策略

你的项目同时开着 Claude Code 的终端会话和 Cursor 的编辑器窗口，琐碎改动还顺手用 Copilot 补两行。一个上午过去，仓库里出现三份互相矛盾的约定：终端里的 AI 按 CLAUDE.md 把接口命名改成了新规范，编辑器里的 AI 按 .cursor/rules 里的旧约定写了新函数，Copilot 则按 copilot-instructions.md 补了一行老式写法。没有人吵架，但代码已经吵起来了。多工具并行的困境不是工具太多，而是每把工具都在按自己读到的那份文档干活，而你从来没有定义过"哪份文档说了算"。

> [!tip] 关键洞察
> 多工具并行的第一原则：仓库里只允许存在一份事实，其他全是引用。AGENTS.md 加 docs/ 目录作为单一事实源，工具专属文件只声明触发规则，不复制事实。事实重复一次，就多一分打架的风险。

## 仓库文档是单一事实源

单一事实源由两层组成：一层是常驻指令 AGENTS.md（或 CLAUDE.md），存放构建命令、测试命令、代码规范、关键约束这些"每会话都要知道"的内容；另一层是 docs/ 目录，存放需求、决策、进度、会话交接这类"需要时再查"的文档。前者回答"这个项目怎么干活"，后者回答"这个项目现在到哪了"。

分工要清晰：AGENTS.md 只写约定，不写状态。状态（做到哪、下一步做什么）写进 docs/progress.md，让工具按需读取和更新。约定和状态分开的好处是：约定不常变，各工具每次加载都能保持一致；状态频繁变，集中在一处更新，谁读到的都是最新版。

工具专属文件的存在要克制。Claude Code 的 CLAUDE.md 如果内容与 AGENTS.md 重复，就只保留一句"以 AGENTS.md 为准"；Cursor 的 .cursor/rules 同样只放触发声明和指向；Cline 的 Memory Bank 是它的私有状态区，允许独立，但其中的决策和进度必须定期同步回 docs/。原则是：**工具专属文件管"加载方式"，仓库文档管"事实内容"**。

## 工具专属文件最少化

每个工具都有自带一套配置文件：.cursor/rules、.clinerules、copilot-instructions.md、CLAUDE.md。文件数量本身不是问题，内容重复才是。最少化的三条做法：

1. 约定只写一次：任何规范，先在 AGENTS.md 里定稿，其他工具文件用一行指向它，不复述。工具 A 改规范时改的是 AGENTS.md，而不是自己的专属文件。
2. 触发规则与事实分离：.cursor/rules 的 .mdc 文件只写"哪些 globs 触发、引用哪份文档"，不写规范正文。
3. 每季度清理一次：删掉已过期的规则文件，合并重复条目，让每个工具的配置都短到一眼能扫完。

> [!tip] 关键洞察
> 判断专属文件是否过度的标准很简单：把某份规范从 AGENTS.md 里删掉，如果没有任何工具会因此读不到该规范，说明你在专属文件里复制了它。复制的规范迟早要打架。

## 并行时的文档同步纪律

多工具并行，同步靠纪律而不是靠自觉。文档更新顺序永远是：先改代码的人，先更新文档。具体节奏：

- 改动代码前：把"要做什么"写进 docs/progress.md 的当前任务区，让其他工具知道自己正在占用哪块地盘。
- 改动代码后：代码提交前，先更新文档——AGENTS.md 的约定有变就改约定，决策有变就写 [[05-产品与开发/AI驱动Web应用开发/02-文档体系篇/05_决策记录ADR|ADR]]，进度有推进就更新 progress.md，做完哪步就勾掉哪步。
- 会话结束时：照 [[05-产品与开发/AI驱动Web应用开发/02-文档体系篇/07_会话交接与变更日志|会话交接与变更日志]] 的清单收尾，让下个工具（无论哪把）打开文档就能接上。

同步纪律反过来的代价很直接：工具 A 完成了功能 A 却忘了更新文档，工具 B 按旧文档开工，把功能 A 的改动当作不存在重写了一遍。两把工具没打架，但一个小时的白工是实打实的。

## 避免两个AI打架的协作规则

代码层面与文档层面的冲突，分别用不同的规则约束。

代码层面的规则：分区作业，每把工具一个明确的工作目录或文件集合，写进 progress.md 的任务区。终端 Agent 管后端模块，IDE 工具管前端页面，Copilot 只做当前文件内的补全。跨界前必须先在文档里声明，不允许两把工具同时改同一个文件。遇到格式冲突，以 git 和格式化工具（如 prettier、ruff）为准，提交前统一跑一遍格式化，让工具的格式差异消失在 lint 环节。

文档层面的规则：先读后写。任何工具开工前，先读 AGENTS.md 和 docs/progress.md，确认最新约定与当前进度；任何工具写文档，都是追加或更新，不是重写。约定冲突时，AGENTS.md 优先于一切专属文件，新约定立即改回 AGENTS.md 并同步各专属文件的指向。

争论落点统一：当两把工具对同一件事给出不同做法，不靠人肉仲裁每次分歧，而是把分歧变成一次显式决策——在 docs/decisions 里记一条 ADR，写明选项、选择、理由，然后所有人（包括所有工具）按新决策执行。决策记录在案，争议就有了终局。

## 现在你应该怎么做

1. 检查你的仓库：如果 AGENTS.md、CLAUDE.md、.cursor/rules、copilot-instructions.md 里存在同一规范的三份复制，立即把它们合并成一份，其余改成一行的指向。
2. 建一个 docs/progress.md，把当前任务、负责人（哪把工具）、文件范围、下一步写进去，作为所有工具的开工必读。
3. 定一条硬规则：任何工具改代码前先更新 progress.md 的任务区，代码提交前先更新文档，连续执行一个迭代周期。
4. 约定下一次冲突处理方式：分歧发生时，把两套做法写下来，选一套，记一条 ADR，宣布终局，不许翻案。
5. 跑一个真实的并行会话验证流程：终端 Agent 和 IDE 工具同时开工，观察文档是否被双方遵守，哪里打架就在哪补一条规则。
