# 想法验证

你在一家小公司做运营，每周要花四个小时把 Excel 表格里的数据手工整理成周报。某个深夜你突然想通：做一个 Web 工具让这件事自动化。这个念头连续一周在脑子里打转，你已经在草稿纸上画好了功能列表，页面布局、数据模型、按钮文案全想清楚了。可每次打开编辑器都卡在同一句话前——这个想法到底值不值得做成一个应用？怕做出来没人用，又怕不做会错过什么。

> [!tip] 关键洞察
> 想法的价值不在想法本身，而在你验证它的速度。AI 把"做出来"的成本压到极低之后，真正昂贵的环节变成了判断。判断做错了，代码写得越快，浪费越大。

## 想法验证四问

给每个想法做一次四问体检，全部通过才值得进入 [[02_需求定义|需求定义]] 阶段。

### 第一问：问题真实吗

找三个真实发生过的场景来证明，而不是用"我觉得大家需要"。问题要具体到某个人、某个时间、某个动作：谁，在什么情境下，因为什么卡住，现在用什么笨办法硬扛。你那位运营同事在每周四下午五点对着表格皱眉，这就是一个真实场景；"提高团队效率"不是。真实问题通常都能讲成一个 60 秒的小故事，讲不出来就是还没想清楚。

### 第二问：有人需要并且愿意付费吗

需要和愿意付费是两回事。免费的替代方案已经存在时，你的产品解决的是"麻烦"还是"痛苦"？麻烦让人皱眉，痛苦让人掏钱。验证付费意愿不需要做完整产品，把解决方案描述给目标用户看，敢报价、敢收预付款、敢承诺上线时间，比一百份问卷都诚实。参见 [[05-产品与开发/独立开发者生存指南/02_Idea筛选与验证：做什么比怎么做更重要|Idea筛选]] 里的付费前置验证思路。

### 第三问：我能做出来吗

拆到技术方案的粒度。数据从哪来，存储放哪，谁维护，有没有必须依赖的第三方服务，第三方服务会不会收费。诚实评估自己现在的能力边界，同时也别把话说死——很多卡点在 AI 协作下已经不再是卡点，[[05-产品与开发/Vibe Coder/01-入门准备/技术栈选择指南|技术栈选择]] 会帮你把能力缺口量化。

### 第四问：维护得起吗

Web 应用上线那天才是责任的开始。域名、服务器、数据库备份、安全补丁、用户问题、依赖升级，每一件都要有人管。独立开发者的通病是只算开发成本不算维护成本：上线三个月后你还会不会愿意为它每个周末花两个小时？这个问题在 [[05-产品与开发/独立开发者生存指南/03_MVP开发策略：最小可行产品的最优路径|MVP策略]] 里有一个配套答案——把维护面压到最小。

## 最小验证：先验证再写代码

四问全部通过，也不该直接打开编辑器。先走"最小验证"，用最便宜的手段证明关键假设，再让代码入场。

验证手段从便宜到昂贵排列：

| 手段 | 验证什么 | 成本 |
|------|---------|------|
| 口头访谈 5 个目标用户 | 问题真实度 | 极低 |
| 一页纸方案文档（含报价） | 付费意愿 | 极低 |
| 低代码原型或手工制作的假界面 | 用户能否理解产品 | 低 |
| 落地页 + 预约登记 | 有没有人愿意留下联系方式 | 低 |
| 手动替用户跑一遍核心流程 | 价值是否成立 | 中 |
| 写完整代码 | 全部假设 | 高 |

大多数想法在前五步就被证伪或修正了。真正的目标不是"证明想法对"，而是"尽早发现想法错在哪"。写代码是最贵的验证手段，应该排到最后。

## 真问题还是自嗨问题

区分标准只有一条：问题是否存在于你之外的其他人身上。自嗨问题有三个典型特征：解决方案先于问题存在（先爱上方案再找问题）；目标用户是模糊的"大家"或"年轻人"；你无法说出任何一个人此刻正在为此受苦。反过来，真问题往往令人不快——它意味着有人每天都在损失时间或金钱，而这个损失可以量化。

> [!tip] 关键洞察
> 一个想法如果无法在 30 秒内说出"谁现在正为此付出什么代价"，它大概率是自嗨。验证的目的不是给想法找支持证据，而是给想法找反例。

## 验证清单

进入开发前，把下面每一项打勾：

- [ ] 能用 60 秒故事讲出目标用户的真实场景
- [ ] 至少访谈过 5 个目标用户，不是朋友和家人
- [ ] 知道用户现在用什么替代方案，成本是多少
- [ ] 至少 3 个用户表示愿意付费，其中有人出过报价或预付款
- [ ] 写清了技术依赖清单和第三方服务成本
- [ ] 明确上线后每周维护投入的上限
- [ ] 想清楚验证不通过时的止损线（比如 2 周内没人注册就停）

## 现在你应该怎么做

1. 拿纸写下你的想法，按四问逐条回答，回答不了就先去补信息，别急着写代码。
2. 今天之内约谈 3 个目标用户，问他们现在怎么解决这个问题，记录他们嘴里的原话。
3. 用一页纸写清产品价值主张和报价，发给至少 5 个潜在用户，看有没有人回复"我愿意"。
4. 全部通过后，才打开下一站：[[02_需求定义|需求定义]]，把验证过的想法翻译成 AI 能执行的需求。

验证阶段不产出代码，只产出判断。判断清楚了，后面的流水线才走得快。想了解整个流水线怎么走，先看 [[01-AI技术/超长项目AI跑/00_MOC_超长项目AI跑中枢|超长项目AI跑]] 的方法论骨架。
