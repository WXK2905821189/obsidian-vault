# 技术选型与项目脚手架

需求文档刚定稿，你打开搜索引擎准备选技术栈，结果陷入了比写需求还深的泥潭：Next.js 和 Nuxt 之争、Tailwind 和 CSS Modules 之争、Supabase 和自建 Postgres 之争，每篇教程都言之凿凿，每个博主都宣称自己的方案是终极答案。你花了两天看完 30 篇文章，结论比出发时更混乱。真正的困境不是选项太少，而是选项太多，而 AI 时代的选择标准已经变了——不再是谁的功能最强，而是谁最不容易让 AI 出错。

> [!tip] 关键洞察
> 在 AI 协作开发中，技术栈的第一评判标准是"主流、常见、样例多"，不是"最强、最新、最优雅"。AI 对越主流的框架生成的代码越可靠，你排错时能找到的资料也越多。冷门技术栈的每一次报错，都是你独自面对的黑盒。

## AI 时代的技术栈最少原则

核心只有一条：**能少一个依赖就少一个依赖**。依赖越少，AI 越不容易出错。

理由有三层。第一，每个依赖都是一份 AI 可能用错的 API，都是潜在的错误源；第二，依赖升级会引入 AI 不熟悉的新版本行为，旧代码可能因此静默失效；第三，依赖之间的版本兼容矩阵是 AI 最容易犯错的地方，少一个依赖就少一个矩阵维度。

技术栈最少原则的落地版本：

| 维度 | 最少方案 | 说明 |
|------|---------|------|
| 全栈框架 | 一个框架干到底 | Next.js（React 生态）或 Nuxt（Vue 生态），前后端共用 |
| 数据库 | 一个托管数据库 | SQLite 起步，数据量大了再换 Postgres/Supabase |
| 部署平台 | 一个平台 | Vercel / Netlify / Railway，选 AI 训练数据里最常见的那个 |
| 样式方案 | 一个方案 | Tailwind 或纯 CSS，不要同时引入多个 UI 库 |
| 认证方案 | 平台自带 | 优先框架官方方案，不自己写 Session 逻辑 |

注意表格里的隐藏逻辑：每个维度只给一个位置，选型就是填空，不是论证。详细决策过程参考 [[05-产品与开发/Vibe Coder/01-入门准备/技术栈选择指南|技术栈选择]]，那里有按场景分流的完整决策树。

## 技术选型决策树

用四层过滤器逐层收窄，每层留下唯一答案：

1. **生态层**：我熟悉什么框架？不熟悉的框架，AI 再强也得自己读文档。先选自己至少写过一次的框架。
2. **数据层**：数据多复杂？个人工具和团队应用都从 SQLite 起步；需要实时同步、用户系统时再升级到 Supabase 这类托管服务。
3. **部署层**：预算多少？$0 预算选 Vercel 免费层，有服务器选 Railway，需要定制环境选自托管。部署平台的坑，参考 [[05-产品与开发/Vibe Coder/02-开发实战/Vibe Coding 迭代防退化指南|防退化指南]] 里对环境的讨论。
4. **样式层**：只有一个问题——能不能只用一个方案？Tailwind 是当前 AI 训练数据最充足的答案，除非你已有明确的纯 CSS 偏好。

四层过滤完，技术栈不超过 4 个组件，而且每个都主流。这时候可以放心让 AI 搭架子了。

## 脚手架初始化清单

选型定案后，动手搭项目骨架。骨架的质量决定后续每个会话的 AI 表现，因为这组文件就是 AI 的"入职培训材料"。

- [ ] **README.md** — 一句话项目简介、技术栈清单、启动命令、目录结构说明
- [ ] **CLAUDE.md / AGENTS.md** — 给 AI 的项目级指令：构建命令、测试命令、代码规范、关键约定，越短越好
- [ ] **docs/PRD.md** — 上一站产出的需求合同，放进版本控制
- [ ] **目录结构** — 按框架官方推荐布局，不发明新结构；AI 对官方布局最熟悉
- [ ] **环境配置** — .env.example 提交到仓库，真实密钥只在本地
- [ ] **版本控制** — 首次提交就做，之后每个功能一个提交，见 [[01-AI技术/超长项目AI跑/05_版本控制与渐进式交付|版本控制]]
- [ ] **.gitignore** — 排除 node_modules、.env、构建产物

> [!tip] 关键洞察
> 脚手架阶段有一个免费红利：把所有"应该遵守的规则"写进 AGENTS.md，之后每个新会话的 AI 都会在开工前读到它。这份文件写得好，等于给每个后续会话都配了一个不犯低级错误的前提。

## 决策写进项目记忆

选型过程容易重复踩坑：三个月后你忘了当初为什么用 SQLite，遇到性能瓶颈直接想换 Postgres；或者 AI 在某个会话里擅自引入一个新的状态管理库，因为"它更现代"。两件事都源于同一个漏洞——决策没有落盘。

选型定案后立即做两件事：

1. 在 README 或独立 ADR 文件里写一条决策记录：**选项、选择、理由、放弃的备选**。一句话也行，但要写。
2. 把关键决策同步进 AGENTS.md 的约束区：哪些依赖是禁区、哪些方案是既定路线、升级需要经过谁。

这条"决策即文档"的习惯，正是 [[01-AI技术/超长项目AI跑/03_架构锚点：用Spec锁定AI不乱跑|Spec锚点]] 的雏形——先用一行字锁住技术边界，后续再用完整 Spec 锁住需求边界。

## 现在你应该怎么做

1. 按四层过滤器，每层写下唯一答案，凑齐你的技术栈，不允许出现"或者"两个字。
2. 打开终端初始化项目，跑通"能启动、能提交、能部署"三件事，再谈写功能。
3. 写一份不超过 30 行的 AGENTS.md，把构建命令、测试命令、代码约定写进去。
4. 写一条技术选型决策记录，放进仓库，并在 AGENTS.md 里点名禁止的依赖。
5. 下一步打开 [[04_Spec驱动开发|Spec驱动开发]]，让 AI 按需求合同开工。

骨架搭完，流水线进入最核心的一段：用 Spec 把 AI 锁在需求轨道上。
