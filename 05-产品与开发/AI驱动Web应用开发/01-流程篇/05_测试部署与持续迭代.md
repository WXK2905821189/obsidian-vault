# 测试部署与持续迭代

AI 在对话框里打出"全部功能已完成，测试通过"，你觉得心里没底。这个"测试通过"到底是它跑了测试，还是它觉得测试会通过？你没有逐个点过页面，没有验证过真实数据流，甚至不清楚它有没有把某个功能改坏。更慌的是下一步：这个东西真的要上线吗？上线之后出问题怎么办？这不是你一个人的困境——把"AI 说做完了"当成"真的做完了"，是 AI 协作开发里最常见的翻车点。

> [!tip] 关键洞察
> AI 说的"完成"只是它自己的评估，不是事实。验证必须分三层做，每一层都由不同主体执行：单元测试交给 AI 守，E2E 用脚本守，人工验收只能你自己来。三层全过，才叫真的做完。

## 三层验证

### 第一层：单元测试

给核心逻辑写单元测试，覆盖率不必追求 100%，但要覆盖 Spec 里每个验收标准对应的逻辑分支。单元测试的价值是建立"回归防线"：这次改 A 功能，测试立刻告诉你 B 功能有没有被波及。[[01-AI技术/超长项目AI跑/06_测试驱动：让AI自己守护质量|测试驱动]] 的核心思想在这里直接复用——让 AI 自己写测试、自己跑测试、自己报告结果，你只抽查测试是否真的覆盖了验收标准，而不是看它自吹"全部通过"。

### 第二层：浏览器 E2E

单元测试证明"逻辑对"，证明不了"页面能用"。用 E2E 工具（Playwright 是当前 AI 最熟的）写关键用户旅程：注册→登录→录一笔账→生成对账单→导出。每个核心流程一条脚本，跑一遍要不了两分钟，却能把"按钮没绑定事件"、"路由跳错"这类页面级错误全部暴露。E2E 脚本写一次，之后每次改动都重跑，这就是你的自动化验收员。

### 第三层：人工验收

自动化测试验证"系统按预期工作"，人工验收验证"预期是否符合用户的预期"。亲自走一遍真实场景，用真数据、真浏览器、真网速。重点看三类东西：自动化测试覆盖不到的体验细节（加载态、空状态、报错文案）；AI 自作主张的设计（它改了你没让改的按钮位置）；以及慢场景（首屏、大数据量页面）。人工验收清单见下一节。

> [!tip] 关键洞察
> 三层验证的比例大概是：AI 跑单元测试占 60% 的工作量，E2E 脚本占 25%，人工验收只占 15%，但只有这 15% 能发现"需求理解错误"。三层各有不可替代的作用，缺一层都会在某个时刻以奇怪的方式反噬。

## AI 完成任务验收清单

每个功能宣称"完成"时，要求 AI 逐条回答，回答不了就不算完成：

- [ ] 单元测试文件在哪，覆盖率多少，跑过几次，全部通过
- [ ] 逐条列出 Spec 里每个验收标准的验证结果，附证据（测试名或截图）
- [ ] E2E 脚本是否覆盖该功能的用户旅程，能否一键重跑
- [ ] 该功能的修改影响了哪些文件，是否有未涉及的功能被触碰
- [ ] 有没有新增依赖，为什么，有没有替代方案

这份清单让"完成"从模糊的承诺变成可核对的证据。AI 回答不了的项，就是它的工作还没做完。追问到它拿出证据为止，别接受"我检查过了"这类口头保证。

## 部署的渐进式交付

测试全过之后，上线方式同样要防翻车。渐进式交付的节奏：

1. **本地全绿** — 单元测试、E2E、人工验收全部通过
2. **内测环境** — 部署到独立的内测地址，自己加 2-3 个真实用户先跑一周，记录所有异常
3. **灰度公开** — 正式域名上线，但保留快速回滚能力（前一个版本的镜像/构建产物不删）
4. **全量** — 稳定运行两周后，清理内测环境，正式进入维护期

每阶段之间设一个明确的晋级条件：内测期间没有出现新的数据完整性错误，才允许公开。回滚能力是渐进式交付的保险丝——任何时候出问题，一键回到上一版本，比现场修 bug 快一个数量级。[[01-AI技术/超长项目AI跑/05_版本控制与渐进式交付|版本控制]] 讲透了版本与回滚的配合方式。

> [!tip] 关键洞察
> 上线的目的不是"宣布完成"，而是"开始收集真实反馈"。第一版最大的价值是暴露你没想过的使用方式，所以部署节奏宁可慢，不可险。慢一周上线损失有限，上线即翻车的信任损失无法量化。

## 迭代循环与版本节奏

上线不是终点，流水线进入循环模式。每个迭代周期的节奏建议以周为单位：

| 周内节点 | 动作 |
|---------|------|
| 周一 | 整理用户反馈，筛出真实问题，改 PRD 和 feature_list |
| 周二至周四 | 走一轮 Spec 驱动开发，一次只做一个功能 |
| 周五 | 三层验证 + 渐进式部署 |
| 周末 | 观察数据，写下一轮的候选清单 |

版本号跟着节奏走：0.x 是内测期（随时可以改行为），1.0 是第一个稳定公开版本，之后语义化版本（2.0、2.1、2.1.1）。版本节奏的意义是给用户一个预期锚点，也给 AI 一个上下文边界——每次大版本升级，都是清理旧 Spec、重写新 Spec 的时机。防止迭代中退化的完整方法在 [[05-产品与开发/Vibe Coder/02-开发实战/Vibe Coding 迭代防退化指南|防退化指南]]。

## 上线后监控与反馈闭环

监控不需要昂贵的工具链，从最便宜的开始：错误日志（上线第一周每天看一遍）、关键路径埋点（注册数、核心功能使用次数）、一个公开的反馈入口（邮件或表单，比聊天群好整理）。反馈闭环的四个环节缺一不可：收集 → 分类 → 排期 → 回访。用户提了一个问题，你在下一版本修好，然后回去告诉提问题的用户"修好了"——这一步让用户从"使用者"变成"共建者"，是最便宜的留存手段。

> [!tip] 关键洞察
> 反馈闭环的价值不在功能改进本身，而在信任积累。每一条"我提的 bug 被修复了"都在给产品充值信任。反过来，用户提了三条问题石沉大海，产品再稳也会被弃用。

## 现在你应该怎么做

1. 今天为项目补上第一份验收清单，下一个"完成"的功能必须带证据才能验收。
2. 写第一条核心用户旅程的 E2E 脚本，跑通它，让这条脚本成为每次改动的标配检查。
3. 制定你的渐进式交付计划：内测环境地址、内测用户名单、晋级条件、回滚方式，写进项目 README。
4. 上线后固定每周一个反馈处理时段，把用户问题分类进 feature_list，形成迭代循环。

五步流水线到此闭环：验证想法、定义需求、搭好骨架、Spec 驱动开发、测试部署迭代。回到 [[01-AI技术/超长项目AI跑/00_MOC_超长项目AI跑中枢|超长项目AI跑]] 看看整套方法论，你就拥有了从想法到持续运营的完整地图。
