# Spec驱动开发

需求合同签好了，脚手架跑通了，你把 PRD 丢给 AI 让它开工。两小时后 AI 交回一个"完成"的页面，你逐项对照 PRD 检查，发现五个功能里两个做对了，两个做偏了，还有一个它自己发明了全新的交互。AI 没有偷懒，它只是把"按 PRD 实现"理解成了"按我对 PRD 的理解实现"。需求到代码之间缺的不是更多对话，而是一条让 AI 必须逐点通过的轨道。

> [!tip] 关键洞察
> 和 AI 协作开发，最贵的不是写代码，而是纠正"按自己理解写的代码"。Spec 的作用不是约束 AI 的自由，而是把自由留给它擅长的地方（怎么实现），把边界锁在它不擅长的地方（实现什么）。

## SpecDD 四阶段流水线

Spec 驱动开发（SpecDD）把每个功能的实现切成四个阶段，每个阶段有明确的输入和输出：

```
Specify → Plan → Tasks → Implement
```

1. **Specify** — 把 PRD 里的功能翻译成一份单功能的详细规格：行为描述、输入输出、边界情况、验收标准。输出：功能 Spec。
2. **Plan** — 让 AI 基于 Spec 写出实现方案：涉及哪些文件、数据结构怎么改、要不要动数据库。输出：实现计划。人在这里确认方案，不确认就改 Spec。
3. **Tasks** — 把实现计划拆成可执行的任务列表，每个任务都能独立验证。输出：任务清单。
4. **Implement** — 按任务清单逐个写代码，每个任务完成即验证。输出：通过验收的代码。

四个阶段一次只推进一个功能，整个流水线见 [[01-AI技术/超长项目AI跑/00_MOC_超长项目AI跑中枢|超长项目AI跑]] 里对长项目节奏的整体描述。

## Spec 锁定原则

贯穿流水线的一条铁律：**需求变更先改 Spec 再改代码**。

AI 和人一样，会把"口头说说"当成"随便改改"。今天你说"对账单能不能加个备注字段"，AI 顺手改了页面；明天你说"导出格式换成 CSV"，AI 又改了导出逻辑；一周后 PRD 和代码已经各说各话，而 AI 的下一次修改建立在已经漂移的代码上，越改越乱。

正确的姿势是：任何变更，先回到功能 Spec 修改对应章节，更新验收标准，然后才允许 AI 碰代码。Spec 是唯一事实来源，代码只是 Spec 的投影。[[01-AI技术/超长项目AI跑/03_架构锚点：用Spec锁定AI不乱跑|Spec锚点]] 详细展开了这条原则在长项目里的完整应用。

> [!tip] 关键洞察
> 判断需求是否漂移有一个简单测试：闭上眼睛，新需求能否直接在现有 Spec 里找到落点？找不到，就必须先改 Spec。改 Spec 是免费的，改代码是昂贵的，先做免费的事。

## 功能清单 feature_list 的 passes 状态机制

多功能的项目需要一个总账本，让每个功能的进度一眼可见。项目根目录维护一份 `feature_list.md`，每个功能一行，带状态标记：

```
| 功能 | 状态 | 备注 |
|------|------|------|
| 项目分账 | ✅ passes | 验收全过 |
| 对账单导出 | 🔄 in progress | Spec 已定，任务拆到 3 步 |
| 多币种换算 | ⏸ deferred | 本期不做，见 PRD 不做什么 |
```

状态机只有四个状态，不允许自创：

| 状态 | 含义 | 进入条件 |
|------|------|---------|
| ⏸ deferred | 暂缓 | 决定本期不做 |
| 📝 spec'd | 已定义 | 功能 Spec 写完，验收标准齐全 |
| 🔄 in progress | 开发中 | 已有一个功能 Spec 被实现 |
| ✅ passes | 通过 | 全部验收标准逐条通过 |

feature_list 是每个会话开工前必读的文件。AI 只看状态为 in progress 的功能，绝不碰其他功能——这份清单就是它的工作许可证。

## 每个功能独立小循环

Spec 锁定原则解决"方向"问题，独立小循环解决"质量"问题。每个功能走一遍四步循环：

1. 写功能 Spec，人确认
2. AI 实现该功能
3. AI 自测：对照 Spec 里的验收标准逐条自检，写出自检结果
4. 人复核：抽查关键验收项，勾选通过，状态改为 passes

小循环的关键在于第 3 步和第 4 步分开。AI 自测是廉价的（它自己就能跑测试），人工复核是昂贵的（你的时间），但两者都不能省。自测抓语法和逻辑错误，人工抓"理解错了需求"的错误——这类错误 AI 永远发现不了，因为它的理解就是错的。

## 一次只做一个功能

多任务并发对 AI 是毒药。一次给 AI 十个功能，它会在十个功能之间共享上下文，互相污染：改 A 功能时把 B 功能的数据结构顺带改了，修 C 的 bug 时影响 D 的页面。每个功能独立小循环 + 串行推进，让 AI 的整个上下文窗口只装一件事，错误率和返工率同时下降。

> [!tip] 关键洞察
> "一次只做一个功能"的本质是给 AI 限流。AI 的工作记忆就那么大，塞得越满，越容易在任务边界上犯错。串行推进虽然看起来慢，但每个功能一次做对，总耗时远低于并行后的大规模返工。

## 现在你应该怎么做

1. 把 PRD 里的功能拆成独立条目，建一份 `feature_list.md`，全部标为 📝 spec'd 之前不写代码。
2. 挑第一个功能，写一页功能 Spec：行为描述、输入输出、边界情况、Given-When-Then 验收标准，人确认签字。
3. 让 AI 输出实现计划和任务清单，你只确认"计划是否覆盖 Spec"，不审查实现细节。
4. 一个功能走完小循环、状态改为 ✅ passes 之后，才允许开始下一个功能。
5. 中途任何需求变化，先改 Spec，再更新 feature_list 备注，最后才碰代码。

每个功能都像走一条窄桥：Spec 是桥栏，验收标准是里程碑，一次只走一个功能就不会掉下去。功能写完后，下一篇 [[05_测试部署与持续迭代|测试部署与持续迭代]] 处理"AI 说做完了怎么信"的问题。
