# 需求定义

你把验证过的想法压缩成一句话："做一个轻量记账 Web 应用。"然后把它原样发给 AI。AI 很热情，半小时后返回一个两百行的页面：预算图表、多币种换算、PDF 导出、AI 智能分类、社交分享，样样都有。你看着屏幕上那个五光十色但没一个功能合心意的东西，意识到问题出在自己身上——一句话想法距离 AI 能执行的需求，中间隔着三层没说清楚的东西。

> [!tip] 关键洞察
> AI 不会替你定义需求，它只会放大你给出的需求粒度。需求说得越模糊，AI 的自由发挥空间越大，返工越贵。PRD 的真正作用，是当人和 AI 之间的合同，把"我以为你懂了"变成"我们写下来了"。

## 从一句话到 PRD 的拆解

拆解不是写作文，是回答四个问题：给谁用、解决什么、边界在哪、怎么算做完。按这个顺序写，每一步都基于上一步的答案：

1. **给谁用** — 目标用户画像与核心场景，写清用户此刻的处境
2. **解决什么** — 用户完成什么任务、得到什么结果，任务用动词描述
3. **边界在哪** — 明确不做什么，见下文"不做什么清单"
4. **怎么算做完** — 每个功能配验收标准，见下文 Given-When-Then

PRD 的篇幅不追求长，追求覆盖。三五个核心功能写透，胜过二十个功能每项三行字。产品经理法则里的"能力思维"在这里同样适用：[[05-产品与开发/Vibe Coder/Vibe Coding 产品经理法则|产品经理法则]] 提醒我们，用户要的不是功能本身，而是功能带来的结果。

## 用户故事与验收标准

每个功能用一条用户故事开头，格式固定：

> 作为一个（角色），我想要（能力），以便（结果）。

紧接着配验收标准，用 Given-When-Then 模板，这是人和 AI 都能逐条核对的机器语言：

> - **Given**（给定）：初始状态与前置条件
> - **When**（当）：触发动作
> - **Then**（那么）：可观察的结果，尽量量化

示例：

```
用户故事：作为一个自由职业者，我想要按项目分账，以便月底能直接发对账单。

验收标准：
- Given 项目 A 下已录入 3 笔收入、2 笔支出
- When 我在项目 A 页面点击"生成对账单"
- Then 页面展示一张表：项目总收入、总支出、结余
- Then 数字与明细之和逐项相等，误差为 0
- Then 提供"导出为 PDF"按钮，点击后下载文件
```

验收标准里每一行都是可测试的。AI 写完代码，逐条对照验收标准自测，人再复核一遍，返工率大幅下降。这与 [[01-AI技术/超长项目AI跑/06_测试驱动：让AI自己守护质量|测试驱动]] 的思路一脉相承：把标准写清楚，让 AI 自己守护质量。

## 需求三级粒度

一句话想法到代码之间，需求要拆成三层，每层服务于不同的读者：

| 层级 | 文档 | 读者 | 粒度示例 |
|------|------|------|---------|
| 产品层 | PRD | 人 | 记账应用，支持多项目分账 |
| 功能层 | Spec / 功能清单 | 人和 AI | 项目详情页，含收支明细与对账单 |
| 任务层 | 任务列表 | AI | 创建 project 数据表；写收支录入表单；渲染对账单表格 |

人负责产品层和功能层的判断，AI 负责功能层向任务层的拆解。三层之间的翻译必须显式发生——每次让 AI 从产品层直接跳到代码，都会丢信息。[[01-AI技术/超长项目AI跑/03_架构锚点：用Spec锁定AI不乱跑|Spec锚点]] 描述的正是如何用功能层文档锁住 AI，让它不越过边界。

## 不做什么清单

PRD 里留一节专门写"不做什么"，往往比功能列表更有约束力。AI 的默认行为是"多做"，看到模糊处就自动补全；不做什么清单就是给它划禁区。

```
本期不做：
- 不做多币种换算（用户集中在单一货币地区）
- 不做移动端适配（第一阶段只做桌面浏览器）
- 不做社交分享与协作（单用户工具）
- 不做 AI 智能分类（规则分类已覆盖 80% 场景）
```

每条"不做"都要写一句原因。有了原因，AI 后续面对类似需求时能理解边界背后的逻辑，而不是机械照搬。这份清单同时也是和用户沟通的护栏——[[05-产品与开发/独立开发者生存指南/03_MVP开发策略：最小可行产品的最优路径|MVP策略]] 告诉我们，砍掉的功能不是损失，是省下的维护成本。

## PRD 是合同，不是文档

PRD 写完之后只有一条使用铁律：**它要放进项目里，让 AI 每个会话都读到**。存放在项目根目录的 docs 或 spec 目录，用 [[01_想法验证|想法验证]] 之后的第一个开发会话把它导入项目记忆。这样每次新开会话，AI 都从同一份合同出发，不会因为上下文丢失而"重新发明需求"。

> [!tip] 关键洞察
> 需求变更不可怕，可怕的是变更只发生在对话里。任何需求调整，先改 PRD 和验收标准，再谈改代码。合同文件不变，代码就不该变——这条规矩是后续 [[04_Spec驱动开发|Spec驱动开发]] 的起点。

## 现在你应该怎么做

1. 把想法写成 3 条以内的用户故事，每条配 Given-When-Then 验收标准，先别管格式，写清楚就行。
2. 给每个功能标上"必须做"、"应该做"、"不做"，把"不做"单独整理成清单并附原因。
3. 把 PRD 存进项目仓库的 docs 目录，第一行写上版本号和修改日期。
4. 下一步打开 [[03_技术选型与项目脚手架|技术选型与项目脚手架]]，把这个 PRD 变成能跑的骨架。

需求定义结束的标志不是"文档写完了"，而是"人和 AI 对同一份合同的理解达成一致"。深度参考 [[05-产品与开发/AI产品经理方法论/02_AI产品的需求定义：从「功能」到「能力」|需求定义]] 的方法论，能帮你把这份合同写到恰到好处的粒度。
