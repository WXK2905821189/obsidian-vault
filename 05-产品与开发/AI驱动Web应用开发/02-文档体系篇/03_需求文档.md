# 需求文档

你让 AI 做一个番茄钟，回来发现它默认 25 分钟工作、5 分钟休息，还自作主张加了任务清单和排行榜。功能不少，但没有一个是你想要的：你要的是能自定义时长、到点播放提示音、在标签页标题上显示倒计时的工具。不是 AI 乱来，是需求文档里没写这些。

给 AI 写需求，不能只说"要一个番茄钟"。AI 会填上所有你没说的空白，而且填得理直气壮。它默认 25 分钟，是因为你没写时长可配置；它加任务清单，是因为你没写"不做"。

## Spec 的章节模板

给 AI 读的 Spec 建议包含八个章节，每节都有明确用途：

1. 概述：两句话讲清功能是什么、解决什么问题。
2. 用户故事：以"作为…我想…以便…"格式写核心场景。
3. 验收标准：Given-When-Then 格式，可逐条勾选。
4. 不做什么：明确排除的功能，防止 AI 自由发挥。
5. 技术约束：必须遵守的技术边界。
6. 反面示例：什么样的实现算错，给 AI 排雷。
7. 依赖：这个功能依赖哪些已有模块。
8. 测试要求：需要哪些测试，覆盖哪些路径。

八节里，概述和用户故事定方向，验收标准和反面示例定边界，其余是执行细节。写不全八节没关系，但第 1、3、4 节不能省。

## Spec 与 PRD 的转换关系

PRD 回答"为什么做"，Spec 回答"做什么、怎么验收"。两者是派生关系，不是两份重复的文档：

- PRD 记录动机、用户、业务背景，回答为什么。
- Spec 从 PRD 派生，写清楚可验收的行为定义。
- 需求变更时先改 PRD 确认动机，再改 Spec，保持派生链完整。

PRD 一行"用户需要专注工具"，落到 Spec 就是上面八个章节。缺了 PRD，Spec 缺"为什么"；缺了 Spec，PRD 缺"怎么算做完"。需求从功能到能力的拆解思路，参见 [[05-产品与开发/AI产品经理方法论/02_AI产品的需求定义：从「功能」到「能力」|需求定义]]。

## 验收标准的 Given-When-Then 写法

验收标准必须能机械判断，最实用的是 Given-When-Then 三段式：

- Given：初始状态，世界长什么样。
- When：动作，用户做了什么。
- Then：结果，系统应该呈现什么。

例：

- Given 一个未开始的计时器，When 用户点击开始，Then 显示 25:00 并每秒递减。
- Given 倒计时运行中，When 用户点击暂停，Then 计时冻结，再次点击继续从原处恢复。

写标准时避免"响应迅速""界面友好"这类形容词。AI 无法判断好坏，只能执行能观察的行为。一条合格的验收标准，任何测试工程师都能直接翻译成自动化用例。

## 不做什么清单为什么重要

"不做什么"是给 AI 的刹车，也是最容易被跳过的章节。AI 的自由发挥大多来自规格空白：你没说不做，它就默认可以做。清单写法：

- 一条一行，明确到功能级，不写模糊的"不要过度设计"。
- 每条"不做什么"对应一次 AI 曾经做偏的教训。
- 排除了什么，往往比包含什么更能定义产品边界。

> [!tip] 把"不做什么"当成项目资产积累：每次 AI 跑偏，就把教训写进这一节，Spec 会越用越准。它与 [[01-AI技术/超长项目AI跑/03_架构锚点：用Spec锁定AI不乱跑|Spec锚点]] 的思路一致——Spec 不是需求说明书，是约束 AI 行为的锚。

## 完整模板与示例

```markdown
---
title: Spec 番茄钟 Web 应用
date: 2026-08-11
tags: [Spec]
---

# Spec：番茄钟 Web 应用

## 概述
一个单页 Web 番茄钟：用户设置工作时长，倒计时到点后播放提示音。无账号、无后端。

## 用户故事
- 作为使用者，我想设置工作时长，以便自定义节奏。
- 作为使用者，我想看到剩余时间，以便知道何时结束。
- 作为使用者，我想在结束时听到提示音，以便不盯着屏幕。

## 验收标准
- Given 首次打开页面，When 加载完成，Then 默认显示 25:00。
- Given 用户修改了时长，When 点击开始，Then 按新时长倒计时。
- Given 倒计时归零，When 计时结束，Then 播放提示音并显示"时间到"。
- Given 计时运行中，When 切换标签页，Then 标签页标题显示剩余时间。
- Given 计时运行中，When 点击重置，Then 时间回到设定值并停止。

## 不做什么
- 不做任务清单、统计、排行榜。
- 不做账号、登录、数据持久化。
- 不做自定义提示音上传。
- 不做多语言。

## 技术约束
- 纯前端，无后端请求。
- 倒计时用 setInterval，误差容忍 1 秒。
- 标签页标题通过 document.title 更新。

## 反面示例
- 计时结束用弹窗打断用户（应为非阻塞提示）。
- 关闭标签页后计时仍继续（无后端，不做）。

## 依赖
- 无。单 HTML 文件即可，可用 vite 构建。

## 测试要求
- 倒计时递减逻辑单元测试。
- 计时结束触发提示音的行为测试。
```

> [!tip] 这份 Spec 的核心价值：任何 AI 拿到它都能写出验收标准可逐条勾选的产品，不需要你再解释第二遍。配合 [[01-AI技术/超长项目AI跑/05_版本控制与渐进式交付|版本控制]]，每条验收标准对应一次提交和验证。

## 现在你应该怎么做

1. 写下一个功能前，先开一个 Spec 文件，填完八个章节再让 AI 动手。
2. 验收标准全部用 Given-When-Then，把"界面友好"这类形容词删干净。
3. 把过去 AI 做偏的点整理进"不做什么"清单，变成长期资产。
4. 大需求先写 PRD 定动机，再派生出 Spec，保持派生链完整。
5. 关联阅读 [[01-AI技术/超长项目AI跑/03_架构锚点：用Spec锁定AI不乱跑|Spec锚点]] 和 [[05-产品与开发/AI产品经理方法论/02_AI产品的需求定义：从「功能」到「能力」|需求定义]]，把 Spec 变成项目的锚点文档。

需求写得越具体，AI 的自由发挥空间越小，返工越少。
