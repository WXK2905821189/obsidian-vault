# 会话交接与变更日志

晚上十一点，你关掉对话，信心满满。第二天早上重新打开，AI 一脸茫然，你不得不从"这个项目是做什么的"开始重新解释。更糟的是，上周一个 AI 犯过的错，这周换了个会话又犯了一遍，因为教训只存在于被关掉的那段对话里。会话之间的鸿沟，是 AI 开发模式下最大的隐性成本。

一次会话结束，所有口头交代都归零。能跨会话存活的，只有写下来的东西。交接不是可有可无的仪式，它是会话之间的桥梁：Session Summary 承接上下文，CHANGELOG 沉淀变更事实，lessons 固化教训。三份文档一起，才构成完整的交接包。缺了任何一份，下个会话都要在信息残缺中摸索。

## Session Summary

每个会话结束时写一份 session-summary，存到 docs/sessions/ 目录，文件名带日期。模板六个部分：

- 做了什么：按功能或模块列出本会话完成的事
- 关键决策及原因：本会话做出的判断，一句话理由
- 遗留问题：没解决、需要下个会话处理的事
- 下一步：下个会话的第一优先动作，具体到可执行
- 修改文件清单：列出动过的文件，标注改动性质
- 关键代码片段：两三段最值得下个会话看到的代码

关键决策及原因这一段最容易偷懒，但它决定下个会话是延续还是重来。AI 看到"把缓存从 Redis 换成内存缓存"不会质疑，看到"把缓存从 Redis 换成内存缓存，因为单机部署且数据量小"才会尊重这个决定。理由写一句，下个会话就少一次推翻重来的可能。完整的决策记录则沉淀到 [[05_决策记录ADR|ADR]]，会话摘要里只需给出指向。

一份完整示例：

```markdown
# Session 2026-08-11 密码重置流程收尾

## 做了什么
- 完成验证码邮件模板，接入 SMTP 发送
- 表单错误提示统一为组件内联样式
- 为发送接口补充三个异常分支的单元测试

## 关键决策及原因
- 邮件发送改为异步队列，因为同步发送会阻塞请求，影响登录页响应

## 遗留问题
- 部分邮箱服务商对测试域名拒收邮件，正式上线需配置独立域名

## 下一步
- 跑通完整重置流程的验收用例
- 在 feature_list 里把 AUTH-003 的 passes 翻转为 true

## 修改文件清单
- src/backend/mailer.py（新增队列逻辑）
- src/backend/routes/auth.py（调整调用方式）
- tests/test_reset.py（新增三个用例）

## 关键代码片段
queue.enqueue("send_reset_mail", email, token)
```

注意"做了什么"写的是结果而不是过程，写"实现了邮件模板"而不是"试了五种模板方案"。过程细节属于对话，交接文档只承载结论和理由。

## 会话结束清单

Session Summary 之外，一个规范的会话收尾要跑完整张清单：

- 更新 docs/progress/progress.md 的焦点、变更、下一步、已知问题
- 同步 feature_list.json 的功能状态和 passes
- 有架构级决策时新增 ADR
- 有对外可见变更时更新 CHANGELOG
- 写过 lessons 的坑，确认是否已在代码或流程层面堵住

[[05-产品与开发/Vibe Coder/04-维护收尾/项目交接与记忆|项目交接与记忆]]强调的正是这个闭环：交接不是把记忆倒进某个文件，而是把记忆分门别类放进对应位置，让每个维度的信息各得其所。清单可以打印贴在屏幕边，每项打钩不超过两分钟，别让收尾比开发本身还重。收尾动作最好在会话还开着的时候让 AI 自己起草，你再花两分钟核对，而不是关掉对话后凭记忆补，凭记忆补的交接永远缺细节。

> [!tip] 关键洞察
> 交接文档的价值不在写，而在下一次读取。写 Session Summary 时问自己：如果明天是另一个 AI 实例接手，它只读这一份文档，能无缝继续吗？能，才合格。

## CHANGELOG

CHANGELOG.md 按 Keep a Changelog 约定维护，面向读者是下一个会话和未来的自己，按版本号组织，每版分四类：

- Added：新增的功能
- Changed：现有行为的变更
- Fixed：修复的 bug
- Breaking：破坏性变更，需要重点标注

Breaking 是最重要的一类。它意味着旧的行为不再成立，读日志的人（或 AI）如果不知道，会在错误假设上继续开发。Breaking 条目要写明影响范围和迁移方式，一句"改了接口"等于没写。版本号语义遵循 [[01-AI技术/超长项目AI跑/05_版本控制与渐进式交付|版本控制]] 的规则，破坏性变更至少升一个 minor 版本。

示例：

```markdown
## [0.4.0] - 2026-08-11
### Breaking
- 移除数据库的 Redis 缓存层，改由应用内存缓存替代，旧接口参数不再兼容
### Added
- 用户导出数据功能
### Changed
- 登录接口响应时间由秒级优化到毫秒级
### Fixed
- 修复密码重置邮件在部分邮箱被判为垃圾邮件的问题
```

## 教训闭环

lessons.md 是 AI 开发模式的特殊产物：把 AI 犯过的错变成流程资产。每条教训记录三要素：错误（发生了什么）、原因（根因是什么）、对策（下次如何避免）。

对策要落到机制层面，而不是"提醒自己小心"。AI 没有自律，只有规则。对策写成"新增功能必须附测试用例"比"以后仔细点"有用十倍，写成"发布前必须跑一遍验收清单"比"注意别漏"有用百倍。教训写进 lessons.md 只是第一步，把它转化成检查清单、测试、提示词约束，才完成闭环。测试层面的防线可以交给 [[01-AI技术/超长项目AI跑/06_测试驱动：让AI自己守护质量|测试驱动]] 的方法落地。

[[01-AI技术/LOOP Engineering/04-方法篇/06_棘轮机制|棘轮机制]]描述的就是这个原理：每犯一次错，就把防错机制往前推一格，让同样的错误没有机会第二次发生。lessons.md 是棘轮的齿，每一条教训都是新齿，转动一次就锁死一类错误。一周积累三五条，一个月后 AI 的犯错率会肉眼可见地下降。

一条典型教训的写法：

| 错误 | 原因 | 对策 |
|------|------|------|
| 重构时删除旧接口的兼容层，线上客户端报错 | AI 不知道旧接口仍被外部调用 | 破坏性变更发布前检查调用方清单，并写入 CHANGELOG 的 Breaking 节 |

表格里的"对策"必须在下次会话前变成可执行的规则，否则这条教训三个月后还是教训。每季度翻一遍 lessons.md，把已内化进流程的条目归档，保持清单短到能一次读完。

## 现在你应该怎么做

下一次会话结束前，按顺序做完三件事。第一，写一份 Session Summary，六段模板填满，存到 docs/sessions/ 目录。第二，跑一遍会话结束清单，把 progress、feature_list、CHANGELOG 逐项更新，有架构决策就顺手写进 ADR。第三，如果这个会话里 AI 犯过错，把教训写进 lessons.md，并立刻落实一条防错机制——要么加测试，要么改提示词，要么更新模板，别让教训停留在纸面上。三个会话之后你会感受到差异：打开对话不再需要热身，AI 开口第一句就是"根据上次的交接，我继续处理密码重置的问题"。这才是会话接力该有的样子。
