# 进度与状态文档

项目进入第四天，你打开对话问 AI"我们做到哪了"，它愣了两秒，给出一个含混的概括，然后开始翻代码文件。翻到一半，它甚至不确定某个功能到底做完没有，因为上个会话结束时没人告诉它。多天开发最典型的崩溃场景：不是代码坏了，而是没人知道项目在哪。

AI 没有长期记忆。上一轮对话里的"已完成"和"还没开始"，换一个会话就是全新的空白。代码能反映现状，但反映不了状态：编译通过不等于功能验收，写了接口不等于用户流程走通。进度必须有一份显式的文字载体，每次会话开始先读，每次会话结束先更新，把状态从对话里搬到文件里。

## 两种形态

进度文档分两层，各司其职：feature_list.json 记录功能清单和完成状态，机器可读，AI 逐项核对；progress.md 记录当前焦点和上下文，人类可读，五分钟读完就能接上手。

feature_list.json 是状态数据库，progress.md 是叙事摘要。前者回答"做到哪了"，后者回答"接下来干什么、为什么"。缺了清单，AI 不知道边界；缺了叙事，AI 不知道为什么当前任务排在最前、优先级是什么。两层都维护，才叫完整的进度文档。

## 功能清单

feature_list.json 的每一项是一个原子功能，带独立状态：

```json
{
  "features": [
    {
      "id": "AUTH-001",
      "name": "邮箱注册",
      "status": "done",
      "passes": true,
      "updated": "2026-08-10"
    },
    {
      "id": "AUTH-002",
      "name": "邮箱登录",
      "status": "done",
      "passes": true,
      "updated": "2026-08-10"
    },
    {
      "id": "AUTH-003",
      "name": "密码重置流程",
      "status": "wip",
      "passes": false,
      "note": "验证码发送接口已通，邮件模板待完成",
      "updated": "2026-08-11"
    }
  ]
}
```

status 字段保留三个取值：todo（未开始）、wip（开发中）、done（完成）。done 与 passes: true 必须同时出现，代码写完了但没验证，只能标 wip。passes 字段是清单的灵魂：false 表示功能已有代码但未通过验证，AI 不得把它当作完成品。passes: false 时附上 note，说明卡在哪一步，下一个会话直接从断点继续，不用重新排查一遍。

> [!tip] 关键洞察
> 一个功能只要没有通过验证，就是未完成。AI 会把"代码存在"误判为"功能完成"，passes 字段就是用来粉碎这种乐观的：false 就是 false，标注清楚卡点，不留模糊地带。

## 细粒度原则

功能拆得越细，状态越真实。200 个原子小功能比 20 个大功能好用一个数量级。

原因有三。第一，小功能的完成标准清晰，"邮箱注册"的验收一句话能说清，"用户系统"谁也说不清。第二，小功能之间天然有依赖关系，拆细了 AI 能按依赖顺序推进，而不是在一个大功能里来回打转。第三，状态粒度决定恢复成本：一个大功能标 wip，等于 30 个小任务全部悬空，下一个会话要从头定位断点。

拆分的标尺：一个功能应当能在一次会话片段里完成并验证。一个 feature 超过一天还完不成，拆。拆到每一条都能用"通过或未通过"回答，AI 的状态汇报就不会再出现"差不多了"。

## 当前焦点文档

progress.md 保持精简，四段结构，每段几行就够：

- 当前焦点：这轮开发的主线任务和它的验收标准
- 最近变更：过去两三个会话完成的事，一两行一条
- 下一步：下个会话要做的第一件事，写到能直接动手的程度
- 已知问题：未解决的 bug、悬而未决的取舍、临时的 workaround

已知问题清单最容易被忽视，但它的价值密度最高。AI 遇到报错时，先查已知问题清单，能省掉一半的重复排查。workaround 必须写明"为什么临时、正式方案是什么"，否则下个会话会把临时方案当成正式方案固化进代码。

一份 progress.md 示例：

```markdown
# 项目进度

## 当前焦点
完成密码重置流程（AUTH-003），验收标准：用户通过邮件链接重置密码并登录。
验证码发送已通，正在处理邮件模板。

## 最近变更
- 2026-08-10 邮箱注册、登录完成并通过验证
- 2026-08-11 密码重置：验证码接口打通，表单页完成

## 下一步
1. 完成 AUTH-003 的邮件模板
2. 验证完整重置流程后，把 passes 翻转为 true
3. 开始 AUTH-004 第三方登录

## 已知问题
- SMTP 在开发环境使用测试邮箱，上线前需换正式服务
- 表单校验错误提示文案未统一，暂用占位文案
```

这份示例每段都短到可以一眼扫完，但信息密度足够 AI 直接开工，不需要翻代码确认方向。

## 每会话协议

两个动作绑定每次会话，缺一不可。

会话开始：把 feature_list.json 和 progress.md 一起交给 AI，让它先更新自己的心智模型，再开始动手。花三分钟对齐，胜过开工后纠正三次方向。这个动作要写进系统提示词，否则 AI 会跳过"读进度"直接"改代码"。

会话结束：把 progress.md 的四段全部刷新，feature_list.json 里涉及的功能逐项更新状态和 passes，已知问题新增或关闭。更新的标准只有一条：下一个会话不需要问任何历史问题就能继续。如果会话中途被打断，也要在恢复的第一时间补上更新，别让断档超过一次会话，否则状态文档本身就会过期失真。

[[01-AI技术/超长项目AI跑/07_跨会话传承：让AI记住上次做了什么|跨会话传承]]的核心机制就是这个：不依赖 AI 的记忆，把状态固化在文件里，让每个会话从同一份事实出发。谁负责更新不重要，重要的是每个会话结束时必须更新，形成肌肉记忆。

## 与 git log 配合

进度文档和 git log 是互补关系，不是重复记录。git log 记录代码层面的变更事实（改了什么、何时改），进度文档记录产品层面的状态判断（这个功能算不算完、下一步干什么）。两者各管一维，缺了任何一边都拼不出完整画面。

git 提交信息里加上功能编号（如 AUTH-003），两者就能互相检索：git log 里查得到某个功能的所有提交，进度文档里查得到某个功能当前的状态。版本发布时对照 [[01-AI技术/超长项目AI跑/05_版本控制与渐进式交付|版本控制]] 的节奏，把 feature_list 里 status: done 且 passes: true 的功能整理进发布说明，一张清单就能生成。

## 现在你应该怎么做

从今天起停掉"凭记忆汇报进度"。第一步，创建 docs/progress/feature_list.json，把当前项目所有功能按原子粒度拆出来，状态如实标注，拿不准完成的标 passes: false 并写卡点。第二步，创建 docs/progress/progress.md，写当前焦点、最近变更、下一步、已知问题，每段不超过五行。第三步，在系统提示词里加"每次会话开始读 docs/progress 下所有文件，结束时同步更新"，并把"结束前更新进度"做成会话收尾的固定动作。坚持一个周期后回看 [[01-AI技术/超长项目AI跑/09_案例复盘：一个真实长项目的全流程|案例复盘]]，你会发现最大的变化不是文档变厚了，而是"我们做到哪了"这个问题，再也不需要猜。
