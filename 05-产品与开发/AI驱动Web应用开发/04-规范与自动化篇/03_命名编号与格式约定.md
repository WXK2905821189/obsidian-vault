# 命名编号与格式约定

项目跑了三个月，文档六十多份。目录里躺着一份"需求最终版"、一份"改改改"、一份"copy of 需求最终版"。ADR 编号从 1 到 3 又冒出一个 2.5，CHANGELOG 里日期倒着排。找一份文档靠翻，比写它还费时间。

命名是文档体系的语法层。内容决定文档值不值钱，命名决定别人和 AI 找不找得到。约定越统一，搜索成本越低；约定越随意，文档越多越像垃圾场。规则本身不复杂，难的是让所有文件、所有提交、所有 AI 会话遵守同一套，所以规则要少、要硬、要能写进检查工具。

## 文档命名规范

知识库内文档统一 NN_主题.md：两位数字序号加下划线加主题。

- 01_项目目录结构规范.md
- 02_Spec与文档状态管理.md

序号表顺序不表优先级，保证目录里排序稳定；主题不用标点、不用 emoji、不用"最终版""最新"这类无信息量的词。同一份文档只保留一个文件，旧版本靠 git 历史恢复，不靠文件名标注。文件改名是破坏性操作，会断掉所有双链引用，改名后必须用全局搜索确认没有残留链接。

## 基础格式约定

命名之外，格式统一同样降低解析成本：

- 日期一律 YYYY-MM-DD，写进 frontmatter 的 date 字段，不用"8月11日""昨天"。
- frontmatter 必填 title、date、tags，按文档类型补充 status、version、commit 字段。
- 列表用 - 开头，任务清单用 - [ ] 与 - [x]。
- 表格用 Markdown 表格，不用空格对齐冒充表格。

格式约定服务于两个读者：人靠它扫读，AI 靠它结构化解析。frontmatter 是 AI 的元数据接口，日期、状态、编号放对字段，AI 才能按字段筛选；放错字段或手写日期，AI 解析时就只能靠猜。

## 功能ID规则

每个功能分配一个功能 ID，T-001、T-002 顺序编号，永不复用。ID 从立项那天登记，功能废除也不回收，保证历史记录里的引用永远有效。

| ID | 功能 | 状态 |
| --- | --- | --- |
| T-001 | 登录 | implemented |
| T-002 | 番茄钟计时 | approved |

ID 是文档、代码、分支、提交之间的胶水，全链路共用这一个编号，详见"功能ID贯穿全链路"一节。功能清单 feature_list.md 只登记活的功能，废弃功能在 SPECS.md 里标 obsolete，两头职责分开。

## ADR 编号规则

ADR 从 ADR-001 起顺序编号，与功能 ID 独立。新决策追加新编号，被取代的 ADR 只改状态为 superseded，不删除、不重新编号。[[05-产品与开发/AI驱动Web应用开发/02-文档体系篇/05_决策记录ADR|决策记录ADR]] 已详述状态机与索引，这里只强调编号纪律：编号是身份的不可变部分，重编等于伪造历史。删除旧 ADR 等于删除决策过程，AI 会把你带回原点重新争论同一件事。

## CHANGELOG 格式约定

CHANGELOG.md 按 Keep a Changelog 的约定组织：按版本倒序，每个版本下分四类条目：

- Added：新增功能
- Changed：既有功能的变化
- Fixed：修复
- Breaking：破坏性变更，单独列出并写清迁移方式

```markdown
## [v0.2.0] - 2026-08-11

### Added
- T-002 番茄钟计时功能

### Breaking
- 登录从微信改为邮箱，旧 Token 全部失效
```

条目必须带功能 ID，与 Spec、提交一一对应。Breaking 条目是 CHANGELOG 里最值钱的部分，AI 读它就知道哪些改动会破坏现有行为，新会话接手的 AI 首先看的就是这一节。

## 语义化版本与文档联动

项目版本用语义化版本 vX.Y.Z，从 v0.1.0 起步：

- major：破坏性变更，升级前必须读 Breaking
- minor：新增功能，对应一份新 Spec 进入 implemented
- patch：修复，不动 Spec 与功能清单

文档与版本联动规则：每次发版，CHANGELOG 加一个新版本块；该版本涉及的 Spec 在 frontmatter 里标 version；feature_list 的功能状态同步更新。版本号是文档和代码共同的锚点，看到 v0.2.0，就知道代码、Spec、CHANGELOG 三者对应同一时刻，这一整套联动依赖 [[01-AI技术/超长项目AI跑/05_版本控制与渐进式交付|版本控制]] 的提交纪律支撑。

## 功能ID贯穿全链路

一个功能 ID 同时出现在五个地方，写法完全统一：

| 位置 | 写法 |
| --- | --- |
| Spec 文件名 | T-002-番茄钟计时.md |
| 分支名 | feature/T-002-番茄钟计时 |
| 提交信息 | feat(T-002): 计时核心逻辑 |
| CHANGELOG | T-002 番茄钟计时功能 |
| feature_list | T-002 番茄钟计时 |

AI 拿到任意一个环节的 ID，就能沿这条链找到其余四个。排查问题时从提交反查 Spec，验收时从 Spec 反查分支，不再靠对话记忆串联。需求文档里"做什么"的粒度，到这里统一成 ID 粒度，两个体系正好对齐。

> [!tip] 编号不是负担，是搜索引擎。文档变多之后，人脑的记忆不可靠，可靠的是 ID 之间的显式引用。编号规则越早定越好，事后补编号的成本是当初定编号的十倍。

## 现在你应该怎么做

1. 花半小时把 docs/ 下所有文档按 NN_主题.md 重命名，删除重复文件，改名后全局搜一遍双链。
2. 建 feature_list.md，给每个功能分配 T-XXX 编号，编号只加不减。
3. 给已有 ADR 补编号，缺失的从 ADR-001 开始补写，别等"有空再补"。
4. 把 CHANGELOG 改成 Keep a Changelog 格式，Breaking 单独列出。
5. 从下一个功能开始，分支名、提交信息、Spec 文件名统一用 feature/T-XXX，全程用一个 ID。
