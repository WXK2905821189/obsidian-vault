# Spec与文档状态管理

需求昨天还说支持微信登录，今天改成只支持邮箱。你直接让 AI 改了代码，一周后验收，登录模块里微信的痕迹还在，specs/ 目录里那份文档描述的仍是最初的方案。打开目录，三份 Spec 都写着"最新"，没有一份标注废弃，没有一份指向正在实现的版本。

Spec 的最大敌人不是写不好，是改乱。需求天然会变，Spec 没有状态，就会变成一锅粥：没有状态标记，AI 分不清哪份能开工、哪份已实现、哪份作废；没有索引，找 Spec 靠翻目录；没有版本对应，代码和文档脱节后谁也不敢动。状态管理把"哪份 Spec 说了算"这个问题变成可查询的字段，而不是靠人的记忆。

## Spec 状态机

每个 Spec 在 frontmatter 里用 status 字段标记当前状态，状态机只有四条：

```
draft → approved → implemented
                ↘ obsolete
draft → obsolete
```

| 状态 | 含义 | 变更规则 |
| --- | --- | --- |
| draft | 草稿，讨论中，内容可大改 | 任何人可改 |
| approved | 已评审通过，可以开工 | 改内容前必须退回 draft |
| implemented | 代码已实现，验收通过 | 内容冻结，只追加变更记录 |
| obsolete | 已废弃，不再实现 | 只允许补充废弃理由 |

状态写在文件头部，AI 读 specs/ 目录时先看状态：只有 approved 和 implemented 的 Spec 才参与当前工作，draft 和 obsolete 的自动跳过。这比让 AI 自己判断"哪份需求还在"可靠得多。需求文档的写作方法见 [[05-产品与开发/AI驱动Web应用开发/02-文档体系篇/03_需求文档|需求文档]]，状态机管的是文档写完之后的生死。

## 谁有权改状态

状态是需求真相的源头，权限要收口：只有人能改状态，AI 只能建议。AI 在会话里提出"这条 Spec 可以标 implemented 了"，人来确认并修改状态；AI 无权自作主张把 approved 退回 draft，否则它会在每次需求摇摆时悄悄改写历史。这条约定写进 AGENTS.md 比写进文档更管用，因为 AI 每次会话都读 AGENTS.md。

## specs 目录组织

单功能单文件，文件名带功能 ID：

```
docs/specs/
├── SPECS.md
├── T-001-登录.md
├── T-002-番茄钟计时.md
└── T-003-数据导出.md
```

规则三条：一个功能一个文件，不合并；文件名为"ID-主题"，ID 是功能唯一标识，编号规则见命名编号与格式约定；功能大得放不下就拆成多个 Spec，不要在文件里分节凑合。文件名里的 ID 是全链路的锚点，分支、提交、CHANGELOG 都用它。

## Spec 索引文件

docs/specs/SPECS.md 维护一张表格，是 specs 目录的入口：

| ID | 标题 | 状态 | 版本 | 对应提交 |
| --- | --- | --- | --- | --- |
| T-001 | 登录 | implemented | v0.1.0 | 3f2a9c1 |
| T-002 | 番茄钟计时 | approved | v0.2.0 | — |
| T-003 | 数据导出 | draft | — | — |

AI 打开 SPECS.md 就能回答三个问题：项目有哪些功能、每个到什么状态、代码在哪。索引比正文短得多，常驻上下文的成本极低，却把整份 Spec 体系串了起来。每次新增或变更 Spec，同步改索引一行，索引错了比 Spec 错了更伤，因为它污染的是全局判断。

## Spec 版本与代码版本一一对应

Spec 的 implemented 状态不是终点，它和代码版本绑定才有意义。frontmatter 里记录 version 和 commit：

```yaml
---
title: T-002 番茄钟计时
status: implemented
version: v0.2.0
commit: 5f8e2a9
---
```

好处有两个：验收时能从 Spec 直接跳到对应提交，反查代码是否符合约定；排查 bug 时能确认当前代码对应哪版 Spec，判断是需求变了还是实现错了。配合 [[01-AI技术/超长项目AI跑/05_版本控制与渐进式交付|版本控制]] 的渐进式交付，每个功能都是一次可回滚的提交加一份状态对应的 Spec。

## 需求变更的标准流程

需求变更按固定顺序走，一步都不能跳：先改状态，再改内容，再改代码。

1. 变更请求到达，先把 Spec 状态从 approved 退回 draft，声明这条需求重新开放。
2. 修改 Spec 内容：验收标准、不做什么、依赖，用版本控制留下 diff。
3. 重新评审，状态回到 approved。
4. 让 AI 按新 Spec 改代码，改完更新 status 为 implemented，并登记新版本。

顺序反过来的代价：直接改代码，Spec 变孤儿，下一个会话的 AI 按旧 Spec 又把代码改回去，需求在代码里来回横跳。[[05-产品与开发/项目管理方法论/04_需求管理与范围控制：如何不跑偏|需求管理]] 管的是"该不该变"，本文管的是"变了以后怎么落地"。

> [!tip] Spec 状态就是需求的真相来源。代码可以错，Spec 状态不能错。AI 判断要不要改代码，靠的是一句话：当前代码符合哪份 Spec 的哪个状态？回答不了，就先别动。

## 现在你应该怎么做

1. 给 specs/ 下每份 Spec 的 frontmatter 补上 status 字段，状态与事实不符的立刻改。
2. 建 SPECS.md 索引表，把现有 Spec 全部登记，每次变更同步一行。
3. 下次需求变更，强制按"先改状态、再改内容、再改代码"走一遍，别跳步。
4. 功能验收后，把 version 和 commit 补进 Spec 头部，建立代码与文档的对应。
5. 每周扫一次 SPECS.md，把长期停在 draft 的 Spec 判 obsolete 或删除，别让僵尸 Spec 污染目录。
