# Docs-as-Code

目录结构建好了，命名规范定了，状态机也跑起来了。三个月后打开仓库：AGENTS.md 里写的技术栈还是旧的，三份 Spec 停在 draft，Templates 文件夹里只有一份没人用过的模板。规范没有失效，只是没人执行。靠自觉维护的文档体系，必然烂在"有空再说"里。

代码不会腐烂，因为有编译、有测试、有 CI。文档同样会烂，但大多数人没给它任何检查机制。Docs-as-Code 只有一句话：把文档当代码管理。进版本库、走评审、有 lint、有 CI 检查，让腐烂在合并之前就被拦住，而不是等三个月后体检。

## 理念：文档当代码管理

文档与代码共用同一套纪律：

- 同仓库、同分支、同提交，改代码和改文档在同一个 PR 里。
- 同评审，文档改动要有人看，不自动合并。
- 同检查，格式、链接、待办标记由工具把关。
- 同版本，文档版本与代码版本绑定，规则见命名编号与格式约定。

这条理念的直接推论：文档没有"草稿区"。草稿也是文件，进版本库，标 status 为 draft，评审通过再改状态。[[01-AI技术/超长项目AI跑/05_版本控制与渐进式交付|版本控制]] 给了文档和代码同样的回滚能力，这是 Docs-as-Code 的地基。文档的每一次改动都有 diff，谁改的、为什么改，全在提交历史里。

## 检查工具

三个工具覆盖文档质量的主要维度：

| 工具 | 检查什么 |
| --- | --- |
| markdownlint | 格式：标题层级、列表、代码块标记、行宽 |
| markdown-link-check | 链接有效性：站内双链、站外 URL 是否可访问 |
| vale / textlint | 文体：术语一致、禁用词表、避免模糊词 |

工具守格式底线，人守内容底线。markdownlint 自动修格式，把人的精力留给内容评审。配置一次，之后每个 PR 都自动跑，不用人记住检查清单。

## Spec 评审流程

Spec 从 draft 到 approved 必须经过人评审，评审通过才允许 AI 开工。流程固定三步：

1. 作者或 AI 写完 Spec，状态标 draft，提交 PR。
2. 人评审：逐条核对验收标准的 Given-When-Then 能否机械判断、不做什么是否覆盖历史教训、依赖是否真实。评审清单对照 [[05-产品与开发/AI驱动Web应用开发/02-文档体系篇/03_需求文档|需求文档]] 的八章节要求。
3. 通过后合并，状态改 approved，AI 才按它写代码。

评审不是走过场，是需求变更的最后一道闸。跳过评审直接开工，省的是十分钟，花的是返工两周。评审意见本身也要留痕：驳回理由写进 PR 评论或 Spec 的变更记录，避免下个会话重提同样的质疑。

## ADR 评审

ADR 同样要评审，规则更轻：至少一个人说可以。[[05-产品与开发/AI驱动Web应用开发/02-文档体系篇/05_决策记录ADR|决策记录ADR]] 要求写明被否决的方案，评审时重点看这条：否决理由是否具体到假设，未来什么信号出现可以推翻当前决策。ADR 评审通过后状态从 Proposed 转 Accepted，这个状态切换本身就是一次留痕。没有评审就标记 Accepted 的 ADR，等于没有共识的共识，AI 照样会推翻它。

## 模板体系

docs/Templates/ 放所有文档模板，与实例分开：

```
docs/Templates/
├── spec-template.md
├── adr-template.md
├── tds-template.md
└── session-template.md
```

模板的规则：每个模板只放结构和占位说明，不放示例内容，防止复制模板后忘了删示例；模板本身要评审，模板改了，已有文档不强制迁移；新文档必须从模板复制，不允许手搓结构。模板是文档体系的一致性来源，[[07-学习成长/知识管理体系/04_知识库的结构设计：从混乱到有序|知识库结构设计]] 里的结构原则同样约束模板。模板没人用时是最大的腐烂信号，说明规范与实操脱节，先查模板再查人。

## CI 中的文档检查

文档检查进 CI，与代码检查并行。每次提交自动跑四件事：

1. markdownlint 格式检查，违规即失败。
2. markdown-link-check 全库链接检查，死链即失败。
3. TODO 待办标记扫描：Spec 里残留的 TODO 汇总到 CI 输出，提醒该功能尚未收尾。
4. 状态机校验：SPECS.md 索引与 specs/ 目录文件一致性检查，防止 Spec 建了不登记。

CI 的意义不是抓人，是让检查零成本。人可以不记得检查清单，CI 每次提交都会记得。本地跑一遍同样的命令，提交前就能发现大部分问题，别把 CI 当唯一的闸门。

## 文档腐烂的五个信号

再好的机制也会漏，定期对照五个信号做体检：

1. AGENTS.md 描述的技术栈与代码不符，指令文件失真。
2. 会话交接停在两周前，日期比代码提交还旧，交接断档。
3. 新功能没有对应 Spec 直接改代码，流程被绕过。
4. 同一功能在 feature_list、SPECS.md、CHANGELOG 三处说法不一，状态失联。
5. Templates 里有模板但无人用，模板脱离实际。

清理节奏：每周顺手修信号 1 和 2，随会话收尾一起做；每个版本里程碑做一次全量体检，修复 3 到 5；每季度审视模板体系，删掉没人用的模板，补上缺的模板。

> [!tip] 文档腐烂的根因是更新没有触发点，靠"记得就更新"必死。把检查交给工具，把触发点绑定到事件（提交、评审、发版），文档才能和代码一起活着。

## 现在你应该怎么做

1. 给仓库加上 markdownlint 和 markdown-link-check 配置，本地先跑一遍，修完所有格式问题再谈其他。
2. 把 Spec 评审流程写进 AGENTS.md，明确"approved 之前 AI 不得开工"。
3. 建 docs/Templates/ 目录，从现有文档抽出 spec、adr、tds、session 四个模板。
4. 在 CI 里加一个文档检查 job，跑格式、链接、TODO 扫描三项。
5. 对照五个信号给当前仓库做一次体检，列出腐烂清单，两周内清完。
