# "AI驱动Web应用开发"知识库建设方案

> **文档类型**：建设方案（审阅版）
> **状态**：待审阅
> **定位**：回答两个问题——把想法做成 Web 应用时每一步该做什么；长期使用哪些文档，才能让 AI 在跨会话、跨版本的开发中始终清晰、不跑偏。与已有知识库互补：Vibe Coder 讲"怎么上手"，超长项目AI跑讲"长项目方法论"，本库把它们整合为一条标准流水线，并补齐工程化文档规范。

---

## 一、为什么需要这个知识库

### 1.1 痛点：想法到应用之间，缺一条可复用的流水线

你（Vibe Coder）已经能熟练用 AI 写代码，但每次启动一个新 Web 应用项目时，仍然会反复遇到同一批问题：

- 想法还在脑子里，怎么把它变成 AI 能执行的需求？直接说"帮我做个 XX 应用"，AI 做出来的总是差很远
- 技术栈怎么选？项目结构怎么搭？每次都要重新纠结
- AI 在单次会话里表现很好，但第二天新开会话，它"忘了"项目的背景、约定、进度，需要重新解释一遍
- 迭代几个版本后，AI 开始"自由发挥"：改了不该改的架构、偏离了最初的需求、甚至把之前明确不要的功能加了回来
- 你无法判断"AI 说做完了"到底做完了没有

### 1.2 行业共识：文档是 AI 的长期记忆

2025-2026 年，AI 驱动的软件开发收敛出一条明确路径：**LLM 本身没有跨会话记忆，连续性完全靠版本控制下的 Markdown 文件承载** [1]。行业里出现了三个标志性变化：

1. **指令文件标准化**：AGENTS.md 在 2025 年成为跨厂商开放标准（被 6 万+ 开源项目和 18-24 个 Agent 工具采纳，2025 年 12 月捐给 Linux 基金会），与 Claude Code 的 CLAUDE.md、Cursor 的 .mdc 规则、Copilot 的 instruction 文件并行 [2][3]
2. **Spec 锁定需求**：GitHub Spec Kit 和 JetBrains 都推广"先写规格、后写代码"的 Spec-Driven 开发，Spec 是人与 Agent 之间的"合同" [4][5]
3. **ADR 回归**：因为 AI"重构成瘾"、会把当初的决策理由重构掉，架构决策记录（ADR）重新成为标配，把推理写进仓库 [6]

### 1.3 已有知识库的分工

你的知识库已经覆盖了部分内容，但零散、未整合：

| 已有知识库 | 已覆盖 | 缺口 |
|-----------|--------|------|
| Vibe Coder | 开发工作流、防退化、README/TODO/ARCHITECTURE 三活文档、项目交接 | 无 Spec/PRD 格式、无 CLAUDE.md/AGENTS.md、无 ADR/CHANGELOG |
| 超长项目AI跑 | L0-L4 记忆体系、SPEC/ADR 模板、会话传承、Context Bootstrap | 方法论层面，缺"文件格式与目录约定的最终规范"、CLAUDE.md 系统化编写、Changelog、docs-as-code |
| AI产品经理方法论 | AI 产品 PRD（需求层） | 未与"给 AI 读的可执行 Spec"打通 |
| 知识管理体系 | 命名规范、MOC 结构 | 与项目 docs/ 目录未衔接 |

### 1.4 本知识库定位

把上面这些整合为一条**标准流水线**，并补齐所有工程化细节：

- **一条流水线**：想法 → 需求 → 技术选型 → Spec → 开发 → 测试 → 部署 → 迭代，每阶段人做什么、AI 做什么、产出什么文档
- **一套文档体系**：7 类长期文档（项目记忆、需求、技术设计、决策记录、进度状态、变更日志、会话交接），每类有模板、有示例、有更新时机
- **一个上下文规范**：CLAUDE.md / AGENTS.md 等指令文件怎么写、层级怎么分、跨工具怎么统一
- **一套实战模板**：从零到一的完整项目文档集，拿来即用

### 2.2 架构设计原则

**原则一：流水线驱动，而非文档罗列**。先讲清楚"想法到应用"每一步做什么，文档是流水线各阶段的"产出物"，不是孤立的知识点。

**原则二：文档即合同**。每类文档都强调"它锁定了什么"——Spec 锁需求、ADR 锁决策、进度文档锁状态。让 AI 不越界的不是提示词，是这些合同文件。

**原则三：与已有知识库互补，不重复**。方法论层面的内容（记忆体系、防退化、PRD 定义）双链引用已有库，本库只写"格式规范、模板、目录约定、整合流程"这些缺失的部分。

**原则四：模板优先，拿来即用**。每类文档都给出可直接复制的模板和真实示例，用户不需要从零发明。

**原则五：跨工具中立**。以 AGENTS.md 等开放标准为主线，Claude Code、Cursor、Cline、Copilot 各自的专属机制作为适配层，避免绑定单一工具。

### 模块二：文档体系篇 — 长期文档全景（核心模块）

**核心理念**：Anthropic 的长跑 Agent 工程实践确立了"文档即交接班笔记"的范式：初始化阶段产出功能清单和启动脚本，每个后续会话先读进度文件再动手 [8]。Cline 的 Memory Bank 把文档体系具体化为 6 个固定文件（projectbrief/productContext/systemPatterns/techContext/activeContext/progress）[9]。本模块融合这两条脉络，收敛为适合个人开发者的一套 7 类文档。

**文档清单**：

| 文档 | 核心场景 | 关键内容 | 篇幅 |

### 模块三：上下文篇 — AI 指令文件编写规范

**定位**：CLAUDE.md / AGENTS.md 这类"AI 指令文件"是文档体系里最容易被忽视、也最影响长期协作的部分。本模块系统讲清楚它们怎么写。

**核心理念**：指令文件的编写有三个行业共识——**渐进式披露**（常驻文件保持精简，细节放独立文件按需读）[10]、**内容取舍**（只放"每个会话都需要知道的事实"，多步流程放规则文件或技能）、**指令要具体可验证**（"用 2 空格缩进"而不是"格式好一点"）[11]。

**文档清单**：

| 文档 | 核心场景 | 关键内容 | 篇幅 |
|------|---------|---------|------|
| 01_AGENTS.md | 你想用一套跨工具的指令文件 | AGENTS.md 的定位与标准；层级加载规则（全局→仓库→子目录，逐层拼接）；内容取舍原则；官方示例拆解（Setup/Code style）；与 CLAUDE.md 的关系（`ln -s AGENTS.md CLAUDE.md` 兼容） | 中篇 |
| 02_CLAUDE.md | 你用 Claude Code，想让每个会话都记住项目 | CLAUDE.md 的四级层级（企业/用户/项目/本地）；"≤200 行"原则及原因；`@path` 导入语法；`.claude/rules/*.md` 按主题拆分；Auto Memory 机制；`/init` 自动生成与 `/doctor` 精简 | 中篇 |
| 03_Cursor规则与Copilot指令 | 你在 IDE 里用 AI 补全/对话 | Cursor 的 `.cursor/rules/*.mdc` 规则体系（alwaysApply/globs/description 三种触发方式）；Copilot 的仓库级指令与路径级指令；两者与 AGENTS.md 的优先级 | 中篇 |
| 04_跨工具统一策略 | 你换了工具，不想重写所有指令文件 | "AGENTS.md 为核心 + 工具专属适配层"的统一策略；一套文档如何在 Claude Code/Cursor/Copilot/Windsurf 间复用；迁移清单 | 中篇 |

### 模块五：工具篇 — 主流工具的记忆机制与选型

**定位**：不同 AI 工具的记忆机制差异很大，选错工具会导致文档体系白搭。本模块帮你选对工具并用对。

**核心理念**：所有工具默认都没有跨会话记忆，差异在于"指令文件怎么加载、有没有自动记忆、会话怎么续接" [1][9]。

## 六、建设原则

1. **每篇文档从一个真实场景开场**。不是"AGENTS.md 是……"，而是"新会话的 AI 完全不记得你的项目，你怎么办？"

2. **模板优先于理论**。每类文档给出可直接复制的模板，用户复制到项目里改一改就能用。

3. **"锁定了什么"是每类文档的核心**。Spec 锁需求、ADR 锁决策、进度文档锁状态——理解这个，才能理解文档体系为什么能约束 AI。

4. **只写已有库缺失的部分**。方法论双链引用，本库写格式规范、目录约定、模板、整合流程。

5. **跨工具中立**。以开放标准（AGENTS.md、docs/、CHANGELOG）为主线，工具专属机制作为适配层。
