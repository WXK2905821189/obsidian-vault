# 文档驱动的变更与防退化流程

三天前登录页还好好的，今天加完"导出 CSV"，登录突然挂了。排查发现，AI 在改导出功能时顺手动了公共的请求封装，参数顺序变了，登录没跟着改。这不是一次手滑，而是没有流程保护下的必然：功能越加越多，改动越来越随意，每次变更都在上一次的地基上打补丁，退化只是时间问题。加一个功能不破坏已有功能，靠的不是小心，而是一条每一步都有检查点的流水线。

> [!tip] 关键洞察
> 防退化的本质不是"少改代码"，而是"每次改动都有据可查、有迹可循"。文档不是负担，而是让 AI 每次只在明确范围内动手的护栏。

## 完整变更流水线

每个功能从想法到合并，固定七步，顺序不可颠倒：

1. **写 Spec** — 把需求写成单功能 Spec：行为描述、输入输出、边界情况、验收标准。没有 Spec 不进入下一步。
2. **评审** — 人审 Spec：验收标准是否可测、范围是否明确、有没有夹带私货。评审不通过就回到第 1 步改 Spec。
3. **建分支** — 从干净的 main 拉出功能分支，分支名带功能标识，如 `feature/AUTH-003-reset-password`。
4. **实现** — AI 按 Spec 写代码，一次只做这一个功能，只动与它相关的文件。
5. **测试** — 为新功能写测试，并跑全量测试确认没有破坏旧的。验收标准逐条对照。
6. **更新文档** — 更新功能清单状态、进度文档、CHANGELOG，有决策就记 ADR。
7. **合并** — 确认测试全绿、文档已同步，再合并回主干。合并前的状态必须是可合并状态。

这七步是 [[05-产品与开发/AI驱动Web应用开发/01-流程篇/04_Spec驱动开发|Spec驱动开发]] 在单功能之外的完整闭环：Spec 管"做什么"，流水线管"怎么安全地做"。

## 防退化检查清单

合并之前，逐项核对这张清单，任何一项不满足就推迟合并：

| 检查项 | 标准 | 不满足则 |
|---|---|---|
| 功能清单回归 | 旧功能状态未被误改，只动目标功能 | 回退越界改动 |
| 测试通过 | 全量测试 0 failed，新增用例覆盖新功能 | 补测试后再合并 |
| E2E 验证 | 登录、下单等关键用户路径跑通 | 修复后再合并 |
| 文档更新 | 功能清单、进度、CHANGELOG 已同步 | 补齐文档再合并 |
| diff 审查 | diff 里只有目标功能的改动 | 拆分无关改动 |

清单的每一行都对应一种典型的退化方式：功能清单回归防"越界改功能"，测试通过防"悄悄改坏逻辑"，E2E 验证防"单元测试全绿但用户路径断裂"，文档更新防"代码和文档脱节"，diff 审查防"夹带私货"。五种退化，五种拦截。

## 一次只改一个功能的限流

流水线最容易被破坏的地方是"顺手"。AI 改 A 功能时顺手改了 B 的一个变量名，顺手优化了 C 的样式。单看每处都没问题，合在一起，git log 变得不可追溯，回滚变得不可能，下次排查无从下手。

限流规则三条：

- 一个分支只承载一个功能，分支内 diff 只允许出现目标功能相关的改动
- 看到无关改动当场拦下：要么拆出去单独处理，要么回滚
- 多个小功能排队做，不并行改；完成一个、合并一个、文档同步一个，再开下一个

[[05-产品与开发/AI驱动Web应用开发/01-流程篇/04_Spec驱动开发|Spec驱动开发]] 里"一次只推进一个功能"的节奏，落到分支层面就是这条限流规则：功能清单是工作许可，分支是工作现场，两者都只允许有一个目标。排队是限流的另一半：手里永远只有一个 in progress 的功能，其余的都在清单里排队。看到两个功能同时半绿，先停一个，把它还原到可合并状态，再继续另一个。

## 需求变更的文档先行

开发到一半，需求变了。最常见的错误做法是直接让 AI 改代码："导出格式加个 CSV 选项"，AI 半小时改完，Spec 里还是旧需求，测试还是旧断言，文档还是旧描述。三份材料各说各话，代码成了一座孤岛。

正确的顺序是文档先行：

1. 先改功能 Spec：更新行为描述和验收标准
2. 再改测试：让测试表达新需求
3. 最后改代码：让代码满足新测试
4. 同步更新进度文档与 CHANGELOG

把"改需求"从一次口头沟通升级为一次文档变更，成本只是多写几行字，收益是 Spec、测试、代码、文档永远指向同一个目标。反过来，代码先行、文档后补的路径几乎必然产生脱节，因为补文档永远排在任务清单的最后，永远补不完。[[05-产品与开发/AI驱动Web应用开发/02-文档体系篇/07_会话交接与变更日志|会话交接与变更日志]] 承接的正是这种"变更落文档"之后的交接。

## 与 Vibe Coder 防退化指南的衔接

[[05-产品与开发/Vibe Coder/02-开发实战/Vibe Coding 迭代防退化指南|防退化指南]] 从 Vibe Coding 的视角讲了防退化的通用打法：基线、测试、回归、记录。本文的流水线是它在文档驱动的 Web 应用开发里的具体化——基线对应可合并状态，测试对应防退化清单，记录对应 CHANGELOG 与 ADR。两套方法可以叠加使用：Vibe Coder 的指南讲原则，本文讲步骤。更大的上下文参照 [[05-产品与开发/Vibe Coder/AI产品开发导航系统|AI产品开发导航系统]]，那里给出了整个 AI 产品开发过程的导航地图。

> [!tip] 关键洞察
> 防退化不是项目后期的事，而是从第一个功能合并进 main 的那天就有的纪律。越早把流水线跑顺，越不需要在项目后期花大价钱收拾退化。

## 现在你应该怎么做

- 下一次加功能，严格走七步流水线，在评审环节多花五分钟，在实现环节省两个小时
- 把防退化检查清单贴进项目的 PR 模板，让每次合并都过一遍
- 检查现有分支：有没有一个分支混着多个功能的改动，有就拆开
- 把"文档先行"写进 AGENTS.md，作为需求变更时的默认动作
- 对照 Vibe Coder 防退化指南，找出本项目的防退化漏洞，补上对应检查项
