# 会话结束协议

深夜十一点，功能写了一半，三个文件改到一半，测试红着两盏。你关掉对话，想着"明天再收尾"。第二天早上 AI 一脸茫然，不知道代码为什么是坏的，也不知道你昨晚为什么要动那个函数。没写交接的会话结束，等于项目的一次失忆：所有改动的理由、未完成的状态、下一步的打算，全部随对话一起消失。结束不是一个时间点，而是一组必须按顺序做完的动作。

> [!tip] 关键洞察
> 会话结束时的十分钟，决定下一个会话开始时的两小时。收尾动作越完整，下个会话越短；收尾越潦草，下个会话越接近从零开始。

## 会话结束六步

按固定顺序执行，每步产出可验证的成果物：

1. **更新进度文档** — 修改 progress.md，记录本会话做了什么、当前焦点落在哪、遗留了什么。回答下个会话的第一个问题："我们做到哪了"。写法见 [[05-产品与开发/AI驱动Web应用开发/02-文档体系篇/06_进度与状态文档|进度与状态文档]]。
2. **更新功能状态** — 把 feature_list 里完成的功能翻到 passes，在做的标 in progress，明确本轮动过哪个功能。
3. **记录新决策到 ADR** — 本会话做出的方向性判断（架构选择、方案取舍、约定变化），写进 [[05-产品与开发/AI驱动Web应用开发/02-文档体系篇/05_决策记录ADR|ADR]]，写明背景、决策、理由、备选方案。
4. **更新 CHANGELOG** — 在变更日志里追加本会话的变更条目：改了什么、为什么改、影响范围。
5. **git commit** — 提交所有改动，写描述性 message（规范见下文），确保工作区干净，不留半成品。
6. **写 Session Summary** — 按模板写会话摘要，存到 docs/sessions/，模板见 [[05-产品与开发/AI驱动Web应用开发/02-文档体系篇/07_会话交接与变更日志|会话交接与变更日志]]。

六步的顺序有讲究：先写文档再提交，commit 里就包含文档更新，下个会话读 git log 就能看到"改了代码加改了文档"的完整记录；先提交再写文档，文档就成了未提交的孤儿，最容易丢。

六步要在同一个收尾动作里一口气走完，不要拆成两次。写了一半的 Session Summary 和没提交的代码一样，都是半成品；隔一夜再补，细节就已经开始丢失。收尾期间不开新任务，只做收尾。

## 文档更新触发规则矩阵

不是每次结束都要更新所有文档，按变更类型对照矩阵：

| 本会话发生了 | 必须更新 | 可选更新 |
|---|---|---|
| 新增或修改功能 | 进度文档、功能清单、CHANGELOG | Session Summary |
| 架构或方案决策 | ADR、进度文档 | CHANGELOG |
| 改动公共代码或依赖 | CHANGELOG、进度文档 | ADR |
| 修复 bug | 进度文档、CHANGELOG | Session Summary |
| 只写文档没动代码 | 进度文档 | 无 |
| 纯讨论没有产出 | 不强制更新 | 记录到 Session Summary |

矩阵的判据只有一条：下个会话读文档时，会不会因为缺这条信息而误解现状？会，就更新；不会，就跳过。宁可多更新一条，不可少更新一条——[[01-AI技术/超长项目AI跑/07_跨会话传承：让AI记住上次做了什么|跨会话传承]] 里讲过，少写一条理由，就可能换来一次推翻重来。

## 环境必须处于可合并状态

收尾的纪律底线：结束前，工作区必须处于"可以随时合并"的状态。三个硬性标准：

- **测试全绿** — 本会话涉及的功能，相关测试全部通过；跑不过的测试要么修好，要么明确标注为遗留问题写进进度文档。
- **没有半成品** — 改到一半的文件要么完成，要么回滚，不把中间态留在工作区。
- **提交即基线** — 收尾的 commit 之后，工作区干净，`git status` 无未提交改动，随时可以开新分支继续。

这条纪律和 [[05-产品与开发/AI驱动Web应用开发/02-文档体系篇/07_会话交接与变更日志|会话交接与变更日志]] 的交接理念一脉相承：交接的不仅是信息，还有环境。一个干净的环境，让下个会话的第一件事不是"清理现场"，而是"继续前进"。可合并状态还意味着回滚成本最低：下个会话发现今天的改动有问题，一个 revert 就能回到干净基线，不必在混乱的工作区里翻找。

## git commit message 规范

commit message 是留给下个会话和未来自己的交接信，写得如何直接决定 git log 的可读性。规范如下：

- 主题行一句话说清"做了什么"，动词开头，不用标点结尾：`feat: 登录页面接入短信验证码`
- 正文用两三行说明"为什么"，而不是重复代码：不是"修改 login.tsx"，而是"短信验证码替代邮箱验证码，因为运营商要求实名"
- 一个 commit 只做一件事，不把无关改动混在一起
- 文档更新和对应代码更新放同一个 commit，保证可追溯

```text
feat: 支持导出 CSV 格式

对账单导出新增 CSV 选项，数据流复用现有报表查询。
选择 CSV 时跳过 xlsx 渲染，避免大数据量下的内存溢出。
```

收尾时的 commit 尤其要写清楚"做到了哪、没做到哪"，因为它是 [[05-产品与开发/AI驱动Web应用开发/02-文档体系篇/06_进度与状态文档|进度文档]] 之外的第二个恢复入口。仓库里很少有 commit 因为"写得太细"被人嫌弃，却常常因为"写得太少"被后人咒骂。拿不准写多少时，按"三个月后的自己能否看懂"来写。

## 结束检查清单

关机前逐项打勾，全绿才结束会话：

- [ ] progress.md 已更新，写明焦点与遗留问题
- [ ] feature_list 状态已同步
- [ ] 新决策已写入 ADR
- [ ] CHANGELOG 已追加本次变更
- [ ] 所有改动已 commit，message 写清"做了什么加为什么"
- [ ] 测试全绿，或遗留问题已记录
- [ ] git status 干净，工作区无未提交改动
- [ ] Session Summary 已写好，存到 docs/sessions/

## 现在你应该怎么做

- 把六步清单存成一张卡片放在手边，前三次收尾对照执行
- 给每次会话定一个收尾闹钟：预计结束前十五分钟开始走六步，别在深夜最困时赶工
- 把 git commit message 规范写进 AGENTS.md，让 AI 起草 commit，你只负责检查
- 从今天起，每次关掉对话前先跑一遍检查清单，连续三次全绿之后，再考虑简化流程
