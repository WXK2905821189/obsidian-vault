# 会话启动协议

昨天收工时的项目状态，只活在昨天那段对话里。今天你打开新会话，输入一句"继续开发登录功能"，AI 回了一声"好的"，然后凭着残缺的印象翻代码、猜结构、下判断。它可能踩进你上周刚填平的坑，可能对着过期的架构写新代码，甚至直接改错文件——因为你没告诉它项目在哪、做到哪、接下来干什么。会话启动不是一句开场白，而是一次信息重建，重建得越彻底，这一天的开发越不跑偏。

> [!tip] 关键洞察
> 新会话里的 AI 不是失忆的旧员工，而是第一天入职的新人。新人要读文档、问问题、复述理解才能上岗，AI 也一样。跳过启动直接写代码，等于让新人第一天就改生产代码。

## Context Bootstrap 标准流程

五步，顺序固定：前四步是读，第五步是跑。

1. **读记忆** — 读项目记忆文档与 AGENTS.md，回答"项目是什么、有哪些约定"。这是 [[01-AI技术/超长项目AI跑/02_上下文管理：AI的记忆体系|AI的记忆体系]] 里常驻层的入口。
2. **读进度** — 读 progress.md，回答"当前焦点是什么、下一步干什么"。
3. **读功能清单** — 读 feature_list，回答"哪些功能已完成、哪个正在改"。只有状态为 in progress 的功能才是工作许可范围，其余一律不碰。
4. **看 git log** — `git log --oneline -20`，回答"最近改了什么、为什么改"。commit message 是上一个会话留下的最短交接。
5. **跑环境验证** — 依次跑构建、测试、lint，回答"当前代码能不能站住"。测试红了就直接停下来修，不要带着一个坏的基线继续加代码。

五步缺一不可。跳过读记忆，AI 会发明约定；跳过读进度，AI 会做错优先级；跳过功能清单，AI 会越界改功能；跳过 git log，AI 不知道昨天动过什么；跳过环境验证，AI 在坏地基上盖楼。整套顺序背后的逻辑，见 [[01-AI技术/超长项目AI跑/07_跨会话传承：让AI记住上次做了什么|跨会话传承]]，那里解释了为什么"读"必须发生在"动"之前。

## 启动协议写进指令文件

让 AI 每次都走这五步，靠人肉提醒不现实。把协议写进 [[05-产品与开发/AI驱动Web应用开发/03-上下文篇/01_AGENTS.md编写规范|AGENTS.md]] 和 CLAUDE.md 的固定章节，作为"会话开工第一指令"。写法要点：

- 用祈使句命令式："每次会话开始，先执行以下五步，全部完成前不得修改任何代码。"
- 给出每个文件的精确路径，不让 AI 自己猜：`docs/memory.md`、`docs/progress.md`、`feature_list.json`。
- 写明验证命令和预期结果："构建通过的标准是无 error，测试通过的标准是 0 failed。"
- 写明复述校验："完成以上步骤后，用三句话复述项目目标、当前进度、本次任务，等我确认后再动手。"
- 把这条指令放在文件最前面，因为 AI 读取长文件时，越靠前的内容遵从率越高。

> [!tip] 关键洞察
> 指令文件的通病是只写"要做什么"，不写"在什么时刻做"。给 AGENTS.md 加上触发条件——"每个新会话的第一条指令"——它就从说明文档变成了真正的协议。

## 动手前的复述校验

即使 AGENTS.md 写得再好，AI 也可能跳过读取直接动工，尤其是遇到"看起来很简单"的任务。因此启动协议的最后一道关卡是复述校验：AI 在改任何代码之前，必须先复述项目背景、当前进度和本次目标，经你确认后才允许动手。

校验的不是复述本身，而是 AI 的上下文是否真的加载了。判断标准三条：

- 背景复述要具体：能说出项目名、目标用户、核心功能，而不是泛泛一句"这是一个 Web 应用"。
- 进度复述要带状态：能说清"登录功能已完成验收，支付功能 Spec 已定、开发中"，而不是"好像做得差不多了"。
- 目标复述要和文档一致：AI 说的本次任务，必须能在 progress.md 或功能 Spec 里找到对应条目。

复述错了不要急着纠正，先让它重读对应文档再复述。连续两次复述不清，直接进入启动失败的排查。

## 会话启动 prompt 模板

复制即用，覆盖五步和复述校验：

```text
开始一个新会话。请严格执行 Context Bootstrap 流程：

1. 读 AGENTS.md 和 docs/memory.md，了解项目背景与约定
2. 读 docs/progress.md，确认当前焦点与下一步
3. 读 feature_list.json，确认哪些功能处于 in progress 状态
4. 运行 git log --oneline -20，说明最近三次提交各改了什么
5. 运行构建、测试、lint，报告当前基线状态

以上五步全部完成后，不要动手改代码。用三句话复述：
- 项目目标是什么
- 当前进度到哪一步
- 本次会话的第一个任务是什么

等我确认后，再开始工作。
```

prompt 的作用不是让 AI 听话，而是给你一个检查点：AI 如果拒绝复述、答非所问，说明它的上下文没有加载成功。此刻拦下，比它改坏代码之后再拦，便宜得多。

## 启动失败的排查

启动流程跑不通时，按症状定位，而不是反复重试同一个 prompt：

| 症状 | 可能原因 | 处理 |
|---|---|---|
| AI 说"没有找到文档" | 文档路径和 prompt 里写的不一致 | 核对路径，用仓库内的实际路径重写 prompt |
| AI 复述时张冠李戴 | 记忆文档过时，旧信息误导了它 | 先更新记忆文档，再重新启动 |
| AI 读完所有文件仍答非所问 | 常驻文档太长，上下文窗口被无关内容占满 | 参照 [[01-AI技术/超长项目AI跑/02_上下文管理：AI的记忆体系|AI的记忆体系]] 的渐进式披露，压缩常驻文档 |
| 测试跑不通 | 上次会话结束时的遗留问题 | 先修基线再启动，或回滚到上次提交 |
| git log 为空或不可读 | 仓库没有提交，或提交信息写得太随意 | 检查仓库状态，补一次基线提交 |

启动失败九成不是 prompt 写得不好，而是底层文档坏了。与其和 AI 纠缠，不如回头修文档——修复一次，所有会话都受益。

## 现在你应该怎么做

- 打开项目，确认记忆、进度、功能清单三份文档存在且为最新，缺哪份补哪份
- 把 Context Bootstrap 五步写进 AGENTS.md 文件的最前面，写明路径与验证命令
- 保存上面的 prompt 模板，作为以后每个会话的第一条消息
- 今天的会话先不急着动手：先让 AI 完成五步并复述，观察它漏掉哪一步
- 按排查表记下这次启动遇到的问题，下个会话开始前先修掉
