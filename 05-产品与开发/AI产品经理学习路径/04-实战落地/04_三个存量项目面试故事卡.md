# 三个存量项目·面试故事卡（框架+提词版）

> [!abstract] 本文用途
> 把你三个最有含金量的存量项目，整理成**可记忆、可自测的面试故事卡**。不是背稿，而是掌握"框架 + 关键词 + 数字"，用自己的话讲。每个项目含：定位卡、STAR 提词表、6 段式提词表、能力边界判断、追问骨架、记忆钩子。
>
> - **代表作①**：知微HR制度问答机器人（RAG+多LLM链）
> - **代表作②**：企业级AI Skill四连发（团队提效）
> - **代表作③**：InterviewPrep 从0到1（AI面试押题 Web 应用）

> [!note] 使用说明
> 记忆原则：**背结构不背句**。每张表只记"关键词触发点"，面试时用自己的话展开。配合 [[05-产品与开发/AI产品经理学习路径/05-进阶出口/02_自我介绍与项目复盘]] 的"录→听→改"打磨法练习，直到不看表也能讲满 1 分钟。

| 句 | 关键词钩子 | 展开要点 |
|----|-----------|---------|
| ① | HR场景三年 + AI落地多产品 | 把 AI 能力翻译成 HR 业务的真实价值 |
| ② | 代表作：RAG制度问答机器人 | 覆盖百余名 HR、分钟级→秒级、解决"胡说八道" |

## 一、代表作①：知微HR制度问答机器人（RAG）

### 项目定位卡

| 项 | 内容 |
|----|------|
| 一句话定位 | RAG 制度问答 + 链路重构，把制度查询从分钟级压到秒级 |
| 主打能力 | 端到端闭环 + 技术判断（反幻觉兜底） |
| 最硬数字 | 分钟级→秒级、编造率↓、覆盖百余名 HR |
| 记忆钩子 | **"不是知识库缺内容，是单条链路过载"** |

### STAR 提词表

| 要素 | 关键词触发点 |
|------|------------|
| S 情境 | HR制度分散（PDF/网页/扫描件）、口径不一、答疑靠翻文档问同事 |
| T 任务 | 建 HR 制度问答机器人，统一制度口径 |
| A 行动 | 一对一诊断 → 错误分类统计 → 定位"单条链路过载" → 按职责拆 4 条链路 + 知识库双向闭环 |
| R 结果 | 分钟级→秒级、编造率↓、会话量不降反升、人工转接↓ |

### 6 段式提词表

| 段 | 关键词触发点 | 必须讲出的数字/判断 | 可抛的追问点 |
|----|------------|-------------------|------------|
| ①背景 | 制度分散、格式五花八门、口径不一 | -- | -- |
| ②问题 | 上线 3 个月后开始编造制度条款、用户"不敢信" | 编造比没人回答严重 | 为什么编造会致命 |
| ③方案 | 一对一诊断 → 错误分类表 → 定位链路过载 → 拆 4 条单一职责链路 | 意图/检索/生成/兜底四条 | 为什么拆链路能治编造 |
| ④我的角色 | 主导根因诊断、链路重构、知识库升级 | -- | -- |
| ⑤指标结果 | 分钟级→秒级、编造率↓、会话量↑ | 覆盖百余名 HR | 指标口径怎么来的 |
| ⑥反思 | 评估先行、棘轮式迭代、方法论比机器人值钱 | 每轮只改一处 | 重来怎么改 |

### 能力边界判断（必讲）

> **编造是生成机制的天生属性，不是 bug** → 不求"让它不编"，而是：**链路拆分 + 严格依据片段**（从根源降低）+ **给出处、引导转人工**（兜底）。

### 追问应对骨架

| 追问 | 回答骨架 | 关键词/可引数字 |
|------|---------|----------------|
| 为什么拆链路能解决编造？ | 编造源于单条提示词职责过载 → 拆单一职责 → 只依据检索片段 → 结构性压缩 | 架构手段，非提示词技巧 |
| 最难的地方是什么？ | 判断根因在哪一层 → 错误案例误导人 → 让数据说话 | 一对一诊断、错误分类统计 |
| 如果重来？ | 一开始就按单一职责建架构 → 评估集从小建立 | 不等爆发再重构 |

## 二、代表作②：企业级AI Skill四连发（团队提效）

### 项目定位卡

| 项 | 内容 |
|----|------|
| 一句话定位 | 4 款 HR 提效 Skill，把"AI 提效"从口号做成团队看得见的改变 |
| 主打能力 | 业务提效 + 团队化落地 |
| 最硬数字 | 建群 4 分钟→1 分钟 |
| 记忆钩子 | **"先找规则明确的机械劳动，再谈技术"** |

### STAR 提词表

| 要素 | 关键词触发点 |
|------|------------|
| S 情境 | 集团 HR 被点名 AI 提效、痛点一眼可见（建群/拆合表/周报/Dify配置） |
| T 任务 | 把高频、规则明确、纯机械的重复劳动自动化 |
| A 行动 | 花一周记录重复动作 → 四问排序 → 选前四项 → 开发四款 Skill → 个人工具升级团队工具 |
| R 结果 | 建群 4→1 分钟、拆合表人工介入递减、周报自动发送、Dify 试错成本↓ |

### 6 段式提词表

| 段 | 关键词触发点 | 必须讲出的数字/判断 | 可抛的追问点 |
|----|------------|-------------------|------------|
| ①背景 | 建群一天几十个/4分钟、考核表拆合、周报2000字、Dify配置手动 | 4 分钟→1 分钟 | -- |
| ②问题 | 高频+规则明确+纯机械+有完成标准、无专职工程师、排期以周计 | 组织号召与技术缺口错位 | -- |
| ③方案 | 先记录再谈技术 → 四问筛选 → 四款 Skill → 个人工具→团队工具三件事 | 降门槛/补文档/留人工审核 | Skill 和脚本的区别 |
| ④我的角色 | 痛点识别→方案→实现→团队交付全流程主导、守数据不出域红线 | -- | -- |
| ⑤指标结果 | 建群 4→1 分钟、拆合表递减、周报自动、Dify 试错↓ | 隐性：团队 AI 接受度↑ | 4→1 分钟会不会太小 |
| ⑥反思 | 四个坑：自动化做过头/只做工具不做文档/忽略合规/急于铺开 | 生成+人工确认+定时发送 | 重来怎么改 |

### 能力边界判断（必讲）

> 四问筛选：**多久做一次？一次多久？出错多大？能不能模板化？** → 全是"规则明确的机械劳动"，不需要前沿模型能力。

### 追问应对骨架

| 追问 | 回答骨架 | 关键词/可引数字 |
|------|---------|----------------|
| Skill 和一般自动化脚本的区别？ | 脚本解决"我的流程" → Skill 是可复用/可交接/有文档/有审核的团队资产 | 个人代码→团队工具是分水岭 |
| HR 不懂技术怎么落地？ | 降门槛 + 文档先行 + 人工审核节点 | 非技术同事能直接用、敢用 |
| 有什么合规考量？ | 数据不出域、输出人工审核、敏感数据留痕审批 | 宁可流程繁琐不裸奔 |

## 三、代表作③：InterviewPrep 从0到1（AI面试押题Web应用）

### 项目定位卡

| 项 | 内容 |
|----|------|
| 一句话定位 | 0 到 1 独立 AI 面试产品，把"猜不到会被问什么"变成闭环 |
| 主打能力 | 需求判断力 + 0 到 1 闭环 |
| 最硬数字 | 16 模块、7 家供应商、准备度 52→71 |
| 记忆钩子 | **"一个人做产品，最值钱的是需求判断力"** |

### STAR 提词表

| 要素 | 关键词触发点 |
|------|------------|
| S 情境 | 小红书高频"面试官视角押题"需求、市面靠人工非标又贵 |
| T 任务 | 做一款 AI 面试押题产品，把"会被问什么"从猜变算 |
| A 行动 | 机会→需求→闭环设计（岗位分析→能力诊断→靶向练习→效果评估）→ 16 模块 P0/P1/P2 → 技术选型"最省维护" |
| R 结果 | 准备度 52→71、五维雷达、60 天热力图、错题集、学习计划 |

### 6 段式提词表

| 段 | 关键词触发点 | 必须讲出的数字/判断 | 可抛的追问点 |
|----|------------|-------------------|------------|
| ①背景 | 小红书"面试官视角押题"帖子、市面人工非标贵 | -- | -- |
| ②问题 | 信息不对称、缺乏针对性反馈、练习无闭环 | 三大痛点 | -- |
| ③方案 | 岗位分析→能力诊断→靶向练习→效果评估闭环、16 模块 P0/P1/P2 | 先让闭环转起来再转得深 | 7 家供应商是否过度设计 |
| ④我的角色 | 需求判断→闭环设计→功能拆解→技术实现→上线运营一人完成 | 最省维护 | -- |
| ⑤指标结果 | 准备度 52→71、五维雷达、60 天热力图、错题集、学习计划 | 投入线+能力线 | 如何衡量成功 |
| ⑥反思 | 需求判断力最值钱、闭环意识、克制（P2 等 P0 验证） | 不服务闭环的功能是成本 | -- |

### 能力边界判断（必讲）

> 需求高频具体 + 大模型能力天然匹配（解析 JD/生成考题/模拟面试官）+ 竞品结构性空档 → 值得做。

### 追问应对骨架

| 追问 | 回答骨架 | 关键词/可引数字 |
|------|---------|----------------|
| 7 家供应商是不是过度设计？ | 独立开发者"最省维护"是标准 → 按场景路由 + 互为容错 | 一家挂了有备选 |
| 如何衡量产品成功？ | 不给功能数量 → 盯准备度曲线 | 52→71 是"真的帮到用户"的证据 |
| 和 ChatGPT 直接问答的区别？ | ChatGPT 不聚焦岗位、不稳定 → InterviewPrep 是闭环 | 从功能到能力的产品化差异 |
