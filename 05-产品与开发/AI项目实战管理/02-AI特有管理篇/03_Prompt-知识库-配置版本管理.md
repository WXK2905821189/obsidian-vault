# Prompt-知识库-配置版本管理：让 AI 资产可回退可对比

> [!abstract] 一句话解决
> AI 项目的"资产"不只是代码，还有 **Prompt、知识库内容、Agent/Skill 配置**。这些资产改起来零成本、影响却巨大——一个 Prompt 改错、一次知识库覆盖、一段配置误改，都能让机器"失忆"。本文给出版本化、可回退、可对比的方法与登记模板，让 AI 资产像代码一样被管理。

---

## 一、为什么 AI 资产也要"版本管理"

### 1.1 三类资产，三类失控

| 资产 | 描述 | 失控反例 |
|------|------|---------|
| Prompt | 系统/用户提示词逻辑 | 改了一个 Prompt，输出风格大变，却不知道改前是啥样 |
| 知识库 | 投喂给 RAG/Agent 的文本、切片、条目 | 上限覆盖旧知识，回答忽新忽旧无法回退 |
| 配置 | Agent/Skill/Prompt集合/温度/检索参数 | Skill 迭代多版，分不清线上哪版、能否回退 |

> 核心认知：**代码有 git 管，AI 资产往往没有任何管护。** 但 AI 资产的"一个字符改动"对行为的影响，往往比代码还敏感——所以更需要版本化。

### 1.2 硬体现：它和"双螺旋页"直接配合

> 第 1 篇《版本对齐表》里每个 Solver 版本的 Prompt/配置快照，就靠本篇这套版本管理来落地。**评测驱动（第2篇）告诉你改哪、本篇告诉你怎么记、怎么回退。**

## 二、版本化的核心要素

### 2.1 一个版本号该包含

> 建议 `{资产类型}-{语义}-v{轮次}` 或加日期，如 `RAG-Prompt-v7` / `zhivei-知识库-20260815`。**关键：日期或序号递增、不覆盖。**

### 2.2 每份资产要存的元信息

| 字段 | 意义 |
|------|------|
| 版本号 | 唯一标识，递增 |
| 内容快照 | 当时完整内容（Prompt原文/知识库文件/配置段） |
| 变更记录 | 改了什么、为什么（动机） |
| 关联版本 | 配套的模型/评测基线（衔接第1、2篇） |
| 是否当前 | 当前线上是哪一版 |
| 作者/日期 | 谁改的、什么时候 |

---

## 三、变更登记表（模板，每处变更一行）

> 任何一次改动（改 Prompt / 覆盖知识库 / 调配置）都在这张表登记。这一张表+内容快照，就是 AI 资产的"git log"。

| 日期 | 资产 | 版本(v从/to) | 改动内容 | 为什么/动机 | 关联基线 | 是否当前 | 回退依据 |
|------|------|------------|---------|-----------|---------|:---:|---------|
| 08-20 | RAG-Prompt | v6→v7 | 增加"引用来源"约束 | 用户反馈缺出处 | 评测R7 | 是 | 可回退v6 |
| 08-12 | 知微知识库 | 07→08 | 新增政策条款8条 | 补业务盲区 | 评测R5 | 否 | 可回退07 |

> 使用规则：
> - **改动必登记**，哪怕"="顺手"。没登记 = 没改。
> - **留下内容快照**，登记表只记索引，快照存文件/备份。
> - 回退到旧版 = 取出对应快照恢复 + 更新"是否当前"。

## 四、可回退的落地手段

```
方案A 最稳：内容快照入库
  每次变更，把"变更前内容+变更后内容"一起存（文件/目录/表格）。
  回退 = 复用变更前内容。

方案B 低成本：登记表指向备份
  关键 Prompt / 配置放有历史记录的文档或 git。
  回退 = 取回历史版本。

方案C 严谨：与评测集绑定
  每个版本登记搭"版本对齐表"与"评测基线"，
  回退 = 回到上一基线的版本组合。
```

> 建议从方案 A 起步（一张表+快照目录即可），再视复杂度升级到基于 git 的完整管理。

## 五、可对比：怎么判断"两版到底差在哪"

| 对比类型 | 做法 |
|---------|------|
| 文本 diff | 对 Prompt / 配置做逐行 diff，看清"措辞变化" |
| 行为对比 | 对同一评测集分别跑两版，看指标差（见第2篇） |
| 组合对比 | 用版本对齐表，找到"哪一版 Prompt+哪版模型+哪版知识库"的组合最优 |

> 关键：**对比不能只看"好像更好"，要落到"具体哪一段变了 + 评测数值变了多少"。** 这才能解释给用户、也才能支撑回退决策。

## 六、实战案例：Skill 封装与多 LLM 链

> 结合你做 Skill、以及在多模型/多链场景的抽象示例改写：

```
场景：你在封装一个"多LLM分工"的 Skill（规划链 + 生成链 + 质检链）。
问题：三条链各有一个 Prompt 和判定配置，调整其一会影响整体输出，
      过去易出现"改坏一道、说不清是哪条链"。

做法：
1. 每条链的 Prompt 单独一个版本号（planPrompt-v3 / genPrompt-v4 / qcPrompt-v2）。
2. 整条 Skill 再给一个"联调版本号"（skill-v5），记录三链当前拼装。
3. 每次只改两条链进一寸，变更登记表记"改哪条、影响哪评测指标"。
4. 出问题时：拉"skill-v4"整份配置快照一键回退；或单回退某链旧版。
5. 配一张版本对齐表，对应 skill 版本 ↔ 模型 ↔ 评测基线。
```

> 结果：多链 Skill 不再是"一团黑盒"，而是可逐链、可整体回退、可向他人解释的资产。这也呼应了你在知识玮"Skill 深化路线图"里的诉求——**让 Skill 可复用、可交接、可版本演进**。
