# 模型迭代×产品迭代：双螺旋怎么管

> [!abstract] 一句话解决
> AI 产品同时有**两条时间线**——模型能力在升级（换模型、调参数、换提示词），产品功能在迭代（加功能、改交互、调流程）。这两条线节奏不同、彼此影响，管不好就会"模型一换，产品全崩，还说不清是谁的锅"。本文给出**对齐机制 + 版本映射 + 回归控制**，让两个节奏可协调、可追踪、可回退。

---

## 一、为什么是"双螺旋"而不是"一条线"

### 1.1 两条独立的时间线

| 时间线 | 节奏驱动力 | 周期 | 最容易失控的点 |
|--------|-----------|------|--------------|
| 模型迭代 | 新模型发布、微调、提示词调优、评测达标 | 快、碎片化（几天~几周） | 频繁换模型却不动产品层 |
| 产品迭代 | 用户需求、功能交付、发布节奏 | 慢、整体化（几周~几个月） | 大改产品而底层模型不稳 |

> 关键认知：**这两个节奏天然不是 1:1 同步的。** 模型可以一周一换，产品不可能一周一重构。强行拉齐，大代价；放任脱节，连锁崩。

### 1.2 你踩过/最易踩的坑（真实场景）

- **"顺手换成新模型"**：知微 RAG 机器人看到笔者更新、或社区说某模型检索更准，随手换上，结果知识库问答风格突变、对用户惯用问法反而变差——**回退时却不知道之前是哪个模型哪个配置**。
- **"先上功能再管模型"**：产品侧加了"追问澄清"功能，但底层检索模型没跟上，新功能命中率低，用户以为功能坏了。
- **"改配置怪产品"**：模型升级后一段 Prompt 不再生效，排查半天，其实是另一条线动的。

> 双螺旋的本质：**模型层的每一次波动，都要在"产品版本"里登记、评估、可回退；产品层的每一次改动，都要问一句"这会不会依赖特定模型行为"。**

## 二、双螺旋的分工与触碰面

```
产品迭代轴（慢）:  功能A → 功能B → 功能C
                            ↓格式化
模型迭代轴（快）:  m1 → m2 → m3 → m4
                            ↑用哪版？何时换？
触碰面:            Prompt | 检索参数 | 温度 | 知识库切片策略 | 输出解析
```

> **触碰面**是两条线唯一互相影响的地方。管理双螺旋，本质是**把触碰面的每次变化都记一个版本**，而不是去管"模型本身"或"产品代码"——那些是各自工具链的事。

### 触碰面清单（哪些东西"换模型会变"）

| 触碰面 | 换模型后可能变 | 你是否登记 |
|--------|--------------|----------|
| Prompt（系统/用户提示词） | 生效写法不同、格式偏好不同 | □ |
| 检索配置（top_k、阈值、重排） | 语义理解力变了，阈值要重调 | □ |
| 生成参数（温度、max_tokens） | 输出风格/长度漂移 | □ |
| 输出解析（JSON 格式约束） | 模型对格式的遵循度不同 | □ |
| 知识库切片策略 | 命中质量波及检索 | □ |

## 三、对齐机制：怎么让两条线不停打架

### 3.1 三个"对齐动作"

1. **降频放行**：模型升级不即时上线，先落地到"影子环境/试用"，观测 1 个评测周期再全量。
2. **版本绑定**：每个产品版本锁定一个"模型快照"（模型 ID + 关键 Prompt 版本 + 参数版本），产品功能与它们一起发布，而不是与"最新模型"一起发布。
3. **回归关卡**：每次换模型前，跑一遍该产品版本的回归评测（见评测驱动篇），不合格就不采纳。

### 3.2 双线节奏的策略矩阵

| 模型侧状态 | 产品侧动作 |
|-----------|----------|
| 新模型在同类任务边更稳 | 可升，但走"变更登记+回归" |
| 新模型在某子任务变差 | 分路由：该子任务锁定旧模型（模型分流） |
| 产品要加依赖模型行为的功能 | 先冻结模型版本，功能稳定后再考虑升级 |
| 模型高速演进期（如大版本发布潮） | 产品侧尽量小步改，减少变量 |

> 一句话策略：**产品想大步快跑时，模型要先锚定；模型想大步升级时，产品先只做小改。**

## 四、模型版本 × 产品版本的映射（核心模板）

> 每个产品版本配一张**版本对齐表**，明确"这版产品跑在哪个模型/哪套配置上"。这张表让"模型问题"和"产品问题"可分离、可回退。

### 模板：版本对齐表

| 列项 | 说明 | 示例（知微RAG机器人） |
|------|------|---------------------|
| 产品版本 | 本产品迭代编号 | v0.4 |
| 发布日期 | 上线/交付日期 | 2026-08-20 |
| 模型ID/版本 | 底层模型精确版本 | deepseek-chat @ 某builder版本 |
| 嵌入/检索模型 | RAG用的向量/重排模型 | bge-m3 v2 |
| Prompt版本 | 触碰面的提示词版本 | RAG-v7 |
| 检索参数快照 | top_k、阈值、温度、切片 | k=4, th=0.52, temp=0.2 |
| 配套知识库版本 | 依赖的知识库快照 | 知微-08-15 |
| 已知已知坑/备注 | 本组合下的弱项 | 英文问题略弱 |
| 是否当前基线 | 是否作为回归对比基线 | 是（基线v0.4） |

> 使用规则：
> - **每个产品版本对应一行**，建立"产品/模型"的固定搭配记录。
> - 换模型/调参数/Prompt 时，**新增一行**，不覆盖老行。
> - 每次改动都设一个"**当前基线**"，回归对比都拿它做锚。

## 五、模型升级的回归风险与处理

### 5.1 四类典型回归

| 回归类型 | 表现 | 根因 |
|---------|------|------|
| 能力回归 | 原来会的题不会了 | 新模型在某子任务变差（需分流） |
| 风格回归 | 回答口吻/长度/结构变了 | 生成参数/Prompt 不匹配 |
| 格式回归 | JSON 解析失败、字段缺失 | 新模型不遵循格式约束 |
| 检索回归 | RAG 命中变差 | 向量/重排模型或切片不匹配 |

### 5.2 处理流程（可执行）

```
发现回归 → 用版本对齐表定位是"模型/参数/Prompt/知识库"哪一层
        → 跑几例回归样例确认 → 决策：
            修补（调参数/微调Prompt）→ 记录为一行新版本
            分流（该任务锁旧模型）   → 加路由规则
            回退（换回上一基线）    → 用对齐表一键恢复
        → 更新基线 → 写进变更记录
```

> 全程关键：**因为版本对齐表里记录了"之前是哪个配置"，回退才有据可依**——这也是第 3 篇《Prompt-知识库-配置版本管理》的铺垫。

## 六、实战案例：知微 RAG 机器人的模型升级

> 抽象示例，可对照你的真实操作改写：

```
场景：知微RAG机器人接入了能力更强的知识库问答，想整体升级底层模型。
Step1 登记：在版本对齐表新增"候选行"，记录新模型 + 沿用旧Prompt，不立即替换。
Step2 影子试用：在非主力入口试用3天，收集真实问答样例。
Step3 回归：用既有错题集/评测集各跑一遍 → 发现"追问澄清"类问题命中率 +12%，
          但"政策条款精确引用"类问题出现2例出处张冠李戴（检索回归）。
Step4 决策·分流：保留新模型做主问答，政策条款类问题锁定旧模型（知识库子路由）。
Step5 回基线：整体回退到基线上的稳定版本发布，把分流规则写进配置。
Step6 存档：新组合记为v0.5行，备注"已验证、含分流规则"。
```

> 结果：从"一换全崩/不敢换"变成"既有升级红利、又有精确回退"。
