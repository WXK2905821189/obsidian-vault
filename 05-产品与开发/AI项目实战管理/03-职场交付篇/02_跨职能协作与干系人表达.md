# 跨职能协作与干系人表达

> [!abstract] 一句话解决
> 向团队/组织交付 AI 项目，最大的墙不是技术，是"**算法/工程/业务各说各话，谁也听不懂谁**"。本文解决两件事：一是怎么**识别干系人、按角色选择影响策略**，二是把你在个人项目里练成的"**个人管理语言**"翻译成团队协作的"**交付语言**"，让不同职能的人都能接得上你的项目。

---

## 一、为什么 AI 项目的跨职能协作格外难

> AI 项目天然跨角色，而且**大家以为的"同一件事"往往不是同一件事**。

| 角色 | 关心的"项目"是什么 | 最容易和你鸡同鸭讲的点 |
|------|-------------------|---------------------|
| 算法 | 模型能力、评测指标、有没有达到那个分数 | 你说"要能用了"，他们问"指标是多少" |
| 工程 | 能不能跑、性能、稳定、可部署 | 你说"功能做好了"，他们问"延迟/并发/挂了怎么办" |
| 业务/产品 | 用户痛点、ROI、什么时候能用上 | 你说"技术实现了"，他们问"价值是什么/何时交付" |

> **个人项目里你一个人身兼四角，答案都默认懂了；进了团队，这四个角色是四个人，默认没人替你翻译。** 跨职能协作的本质，就是**建立一套各方都认的"中间翻译层"**。

---

## 二、干系人识别与影响策略

> 通用理论见 [[05-产品与开发/项目管理方法论/06_干系人管理：把关键人变成同盟]]，这里给 AI 场景下的可操作法：**先识别、再定性、后分层应对**。

### 2.1 干系人画像四问（AI 项目定制版）

1. **他在这项目里要什么？**（指标?稳定?交付时间?背书?别躺枪?）
2. **他卡我还是帮我？**（动力/阻力）
3. **他要的信息密度和语言是什么？**（指标型 / 排期型 / 价值型）
4. **他希望在什么节点被通知？**（越早越好 / 只用讲结果 / 出事才找）

> 别把所有干系人一锅端。**用同一套"算法语言"跟业务讲，或反过来，等于在制造沟通债。**

### 2.2 按角色的影响策略矩阵

| 干系人 | 他们的核心诉求 | 你的影响策略（动作） | 交付语言 |
|--------|--------------|--------------------|---------|
| 算法 | 评测达标、可解释、不被背锅 | 用**评测数据**说话，给可回退两极 | "这版在××指标到××，退化点已分流锁定旧版本" |
| 工程 | 稳定、可控、可部署 | 给**接口/约束/**兜底，别突然改模型 | "改动走版本对齐，理论错误自动回退，延迟到××" |
| 业务/产品 | 价值、时间、ROI | 给**里程碑+可演示成果**，别讲技术细节 | "这版能用用户解决××，X月X日能用上，带来××" |
| 决策/管理层 | 风险、进度、投入产出 | 给**一页风险+预期**，要什么答什么 | "三个风险、一个推迟项、建议的取舍如下" |

> 一句话：**对算法讲指标、对工程讲约束、对业务讲价值、对决策讲风险。同一件事，用四种语言包装，而不是说四遍。**

### 2.3 分层应对节奏（何时用什么策略）

```
T0 需求对齐（早期）: 把"问题/边界/判断标准"说清 → 建立共同词典
T1 进展同步（每周）: 给每个人都"能听懂的一行进展" → 维持信任
T2 关键变更（随时）: 影响谁的变更先通知谁 → 防躺枪/防背锅
T3 冲突升级（遇卡）: 分歧不上桌，先私下对齐、再正式决策 → 留退路
```

> AI 项目特有的坑：算法/工程/业务三方**对"什么叫成功"往往没有共同标准**。所以 T0 阶段花最多时间对齐"成功长什么样"，是跨职能协作里最高杠杆的动作。

## 三、把"个人管理语言"翻译成"团队协作交付语言"

> 你在个人项目里练的那套（里程碑、周自检、闭环、错题集）**本身没问题，问题是表达方式**。个人语言是自己听得懂，交付语言是**在这个团队里大家都听得懂**。

### 3.1 个人词→团队词的翻译表

| 个人管理语言（自用） | 团队协作交付语言（对外） |
|---------------------|----------------------|
| "我这个项目想清楚了" | "已明确用户痛点+P0闭环，判断标准如下" |
| "这周搞定了两个功能" | "本周交付里程碑：××、××，附可演示成果" |
| "评测好像还行" | "对标准评测集，指标从××到××，附样例" |
| "这里不太好搞" | "风险项：××，影响××，建议取舍/需×帮忙" |
| "我把坑踩了一遍" | "已沉淀错题集→转成常见坑清单，供团队复用" |
| "先这么着吧" | "已定验收标准，未达标项为：××，计划×修" |

> 规则：**个人语言的默认听众是自己，交付语言的默认听众是对这事一无所知但对结果负责的人。** 翻译的关键不是堆术语，而是**把"我在干嘛"改成"交付了什么/还差什么/要谁做什么"**。

### 3.2 一段"跨职能对齐"的标准模板（每周）

```
本周交付：可演示成果 + 一行价值说明
   ——给工程：改了哪些接口/配置，影响谁
   ——给算法：指标变化（评测得分/样例）
   ——给业务：用户价值 / 离交付还有多远
风险与待决：列出需要谁拍的板（不要只报而不求助）
```

> 反例（个人语言直出的反面）：
> - ❌ "我升级了 Skill，效果好了很多。"→ 谁？影响谁？好了多少？要不要审？
> - ✅ "Skill 输出格式改版，回归评测提升×%，需工程确认接口兼容、业务验收格式，走 L2 审核。"

## 四、实战案例：跨部门交付时怎么对齐算法/工程/业务

> 以你知微 RAG 机器人和 Skill 跨部门落地为原型：

```
场景：你要把一个带 RAG 的内部问答工具（或一个 Skill）交付给多部门用。
T0·对齐成功标准：
  Step1 拉起算法/工程/业务各一负责人，一起定义"什么叫能用"：
       业务说"能一次答对"，算法说"检索命中率>90%"，工程说"接口延迟<1s"
  Step2 把三方标准写成一页「验收清单」，大家签名确认 → 避免后面翻旧账。
T1·每周一聊句同步：
  Step3 每周给三方各投递其语言的一行：工程听接口改动、算法听评测数、业务听可用程度。
T2·关键变更先通知：
  Step4 模型/配置要动时，先告诉工程"影响哪些接口、能否回退"，再谈"要不要升"。
T3·冲突不上桌：
  Step5 业务要"快上"，工程要"稳"，先在私下达成"取中间档+分批放量"再上会，不硬刚。
结果：三方都能用自己关心的语言接住项目，从"各说各话推卸责任"变成"各守其职共同交付"。
```

## 五、可直接用的「跨职能交付一页纸」模板

> 每次向团队同步/交付前填这一页。填不满说明你没对齐好。

```
【一句话】这个交付解决__的痛点，可交付成果是__
【给算法】评测:____(指标→新值，退化点:____已锁)
【给工程】变更:____(接口/配置/依赖)，影响____，回退方案____
【给业务】上线上:____，用户获得____，ROI/价值____
【给决策】风险:____，建议取舍:____，需谁拍板:____
【验收】三方验收标准:业务____/ 算法____/ 工程____(都已确认)
```

## 六、行动清单

- [ ] 为自己当前 AI 项目拉一张「干系人画像四问」，标出每人的语言/诉求/通知节点
- [ ] 把个人项目那一套"里程碑/评测/风险"翻译成给工程/算法/业务各一条话术
- [ ] 每次对外同步改用「跨职能交付一页纸」，先对齐"什么叫成功"
- [ ] 遇到三方分歧，先在私下对齐再上桌，不评判不硬刚
- [ ] 把 T0 阶段"对齐成功标准"当作最高杠杆动作优先做
