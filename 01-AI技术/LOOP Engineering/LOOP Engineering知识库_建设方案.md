# LOOP Engineering知识库建设方案

> **文档类型**：建设方案（审阅版）
> **状态**：已执行完毕
> **定位**：系统掌握如何设计、构建并持续优化AI Agent的反馈循环，将LLM从"单次问答机"升级为"持续决策循环"。

---

## 一、为什么需要这个知识库

### 1.1 背景与痛点

2025-2026年，AI Agent从"演示"走向"生产"，但大量Agent项目卡在同一个问题：单次调用的质量已经不错，一旦进入多步循环（推理→行动→观察→再推理），系统就开始失控——跑飞、重复、成本失控、结果不可验证。

核心痛点：

| 痛点 | 表现 |
|------|------|
| 循环失控 | Agent陷入无限循环或偏离目标，没有终止机制 |
| 结果不可验证 | 循环产出好坏全凭人工看diff，无法自动化验收 |
| 成本爆炸 | 多轮循环叠加token消耗，账单失控 |
| 状态丢失 | 多步执行中上下文膨胀，Agent"忘记"早期约束 |
| 黑盒运行 | 循环过程不可观测，出错无法回放排查 |

### 1.2 知识库定位

LOOP Engineering（循环工程）是研究"如何设计、运行、持续改进AI Agent反馈循环"的工程学科。本知识库聚焦：

- **Loop的本质**：从Prompt到Loop的范式转移——为什么单次Prompt不够，需要循环
- **五大循环模式**：ReAct、Plan-Execute、Reflection、Ralph、高级模式（ToT/GoT/多Agent）
- **工程化架构**：Inner/Outer双循环、DPEV-I五阶段闭环、Hook+Loop+Harness范式
- **质量与安全**：验证机制、安全护栏、终止条件、成本控制
- **持续进化**：棘轮机制——每次错误转化为规则，系统越跑越准

## 三、核心概念速览

### 3.1 从Prompt到Loop的演进

```
单次Prompt：Q → A（一次性问答）
↓
多轮对话：Q1 → A1 → Q2 → A2（上下文累积）
↓
Agent Loop：目标 → 推理 → 行动 → 观察 → 再推理（闭环执行）
↓
工程化Loop：Hook校验 + 终止条件 + 状态管理 + 可观测性（可控的循环）
```

### 3.2 五大循环模式对比

| 模式 | 核心机制 | 适用场景 | 关键风险 |
|------|---------|---------|---------|
| ReAct | 推理-行动-观察交替 | 需要工具调用的任务 | 循环漂移、成本高 |
| Plan-Execute | 先规划再执行，可重规划 | 多步骤复杂任务 | 计划与执行脱节 |
| Reflection | 生成-反思-修正 | 质量敏感的输出 | 过度反思、发散 |
| Ralph | 外部Stop Hook + 状态机 | 高可靠性生产场景 | 实现复杂度高 |
| 高级模式 | ToT/GoT/多Agent | 探索性、协作性任务 | 状态空间爆炸 |

### 3.3 Hook + Loop + Harness范式

- **Hook**：循环中的检查点（校验钩子），在关键节点强制校验，失败即介入
- **Loop**：核心执行循环，负责推理与行动
- **Harness**：外部约束框架，管理状态、上下文、终止、安全

三条黄金法则：
1. 结果可自动验证，否则循环只是把审查压力往后推
2. 可观测性是1，其他是0
3. 简单优先——能单轮解决的不做两轮
